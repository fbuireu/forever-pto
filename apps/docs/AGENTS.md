# apps/docs

## Purpose

The Forever PTO documentation wiki (docs.forever-pto.com). An Astro Starlight site that documents the app end-to-end and renders the **real** design-system components as React islands, styled by the app's own tokens.

## Boundaries

- Independent workspace package (`forever-pto-docs`) with its own CI ([`.github/workflows/docs.yml`](../../.github/workflows/docs.yml)) and Cloudflare Worker (static assets). It never imports app code as a workspace dependency, only raw sources. Most of that goes through the `@ui` alias, but **not all of it**. Other things reach across:
  - [`HowItWorksDemo.tsx`](./src/components/demos/HowItWorksDemo.tsx) imports `Strategy` from `apps/web/src/domain/calendar/types.ts` and `LOCALES` from `apps/web/src/infrastructure/i18n/locales.ts`, and [`EffectsDemo.tsx`](./src/components/demos/EffectsDemo.tsx) and [`TabsDemo.tsx`](./src/components/demos/TabsDemo.tsx) import `Strategy` and the app's `en.json`, all by relative path. [`PlanningEngineDemo.tsx`](./src/components/demos/PlanningEngineDemo.tsx) imports `PTO_CONSTANTS` from `apps/web/src/domain/calendar/const.ts` the same way, and renders the tunables table through a `Record` that is exhaustive over every leaf of that object, so a tunable added or renamed in the engine fails `astro check` here until its row is written.
  - [`src/lib/app-version.ts`](./src/lib/app-version.ts) reads [`apps/web/package.json`](../web/package.json) for the version the site displays, and [`src/lib/mermaid-render.ts`](./src/lib/mermaid-render.ts) reads the app's `global/index.css` for the diagram palette.
  - [`src/styles/global.css`](./src/styles/global.css) `@import`s **app** stylesheets from `apps/web/src/ui/styles`: `theme/index.css`, `global/index.css` and `utilities/index.css`.
  - Its `@source` directives point somewhere else again: at `apps/web/src/ui/modules/core` and at `apps/web/src/ui/modules/pages/homepage/sections/shared.ts`, so Tailwind generates the utilities those files name. A `@source` only extracts class strings, so scanning Next-coupled files (`Sonner`, `RichLink`) is harmless; `shared.ts` holds the homepage pattern constants (`brutCard`, `dayCell`) that the Homepage pattern page demos, and their classes live outside `core`.

  [`tests/docs-consistency.test.ts`](../../tests/docs-consistency.test.ts) derives that whole reach from the sources and asserts every path of it appears in `docs.yml`'s `DOCS_PATHS`, so a new import that the docs workflow would not rebuild on fails the app's own suite; reaching for a new app module means adding its path to `DOCS_PATHS` in the `changes` job. It scans every file of the package but the Markdown and MDX, so an MDX page takes an app constant from outside `apps/web/src/ui` through a demo module that re-exports it (`APP_LOCALES`, `PTO_CONSTANTS`), never by relative path.

  **That rule proves the docs workflow rebuilds on a change over there, not that the target still exists**, and `astro check` cannot help: it does not read CSS. A second rule resolves every relative `@import` and `@source` against the tree. [`e2e/tailwind-sources.spec.ts`](./e2e/tailwind-sources.spec.ts) proves the `@source` directives still generate the app's classes: a dead one builds green and ships the demos unstyled, which [`e2e/demos.spec.ts`](./e2e/demos.spec.ts) cannot see because it asserts a 200, a child count and a silent console. `docs.spec.ts`'s Button case is no proof of it: `shadow-[var(--shadow-brutal-btn)]` is also written in [`src/components/demos/HitAreaDemo.tsx`](./src/components/demos/HitAreaDemo.tsx), inside this package, so Tailwind generates that rule from the docs root whatever the `@source` does.

  So each probe is a class **this package's own sources never name**, derived rather than hard-coded: `tracking-[…]` read out of [`Button.tsx`](../web/src/ui/modules/core/primitives/Button.tsx) for the `core` directive, `[contain:…]` read out of [`shared.ts`](../web/src/ui/modules/pages/homepage/sections/shared.ts) for the homepage one. Each case asserts the probe is still on the rendered element before asserting the property resolved, so a component that drops the class fails as *pick a new probe* rather than as a broken seam. The `@import` half needs no case of its own: `docs.spec.ts`'s theme toggle reads `--frame` off `:root` and fails if the app's token sheets stop arriving.
- **The logo is the app's, copied rather than referenced.** [`src/assets/forever-pto-logo.png`](./src/assets/forever-pto-logo.png) is a byte copy of `apps/web/public/static/images/forever-pto-logo.png`, the one file the app renders in both themes (what follows the theme is the frame and the shadow, through `--frame`, not the image), because Starlight's `logo` option resolves inside this package and a path out of it is not an asset the build can process. [`src/components/SiteTitle.astro`](./src/components/SiteTitle.astro) draws it the way the app's header does, in a tilted accent box that straightens on hover, beside the version chip. A new logo in the app is two files to copy here: the PNG and `public/favicon.ico`, which is `apps/web/src/app/favicon.ico` byte for byte.
- **The font families are spelled in more than one place and not all of them are tied.** [`apps/web/src/app/fonts.ts`](../web/src/app/fonts.ts) is the source of truth: `next/font/google` registers `--font-bricolage`, `--font-space-grotesk`, `--font-instrument-serif` and `--font-jetbrains-mono`, and the app's `theme/index.css`, imported above, points `--font-sans` and its siblings at those names. There is no Next here to inject them, so [`src/styles/global.css`](./src/styles/global.css) declares the same names in `:root` over the self-hosted `@fontsource` faces. Swap a family in the app and the role token points at a variable this site never defines, so the wiki renders in the browser default while the specimen beside it still names the old family. The contract suite asserts every registered variable is declared here. The remaining spelling is `TypeSpecimen`'s human-readable `label`, which stays prose; nothing mechanises that half.
- **The `@ui` alias is declared once, in [`tsconfig.json`](./tsconfig.json), and [`astro.config.ts`](./astro.config.ts) derives the vite alias from it.** Both files resolve against this directory, so the string needs no adjustment. Move the app's UI layer and there is one line to change. The contract suite fails on any `../web/` path spelled in `astro.config.ts`, which is why its six `locales` are written out rather than read from the app's `LOCALES`: keep the two lists equal by hand.
- **This site declares only the `@ui` alias and runs no Next**, so a module a demo imports, and every module it imports in turn, can reach no other alias and nothing from `next/*` or `next-themes`; a module that does is documented, not imported. `types.ts`, `const.ts` and `locales.ts` import nothing, which is what lets the demos reach them by relative path.
- **[`Demo.tsx`](./src/components/Demo.tsx) supplies the app contexts every demo needs**: `LazyMotionProvider` for every `m.*` consumer and `DemoIntlProvider` for the `next-intl` ones in `core/` (`SlidingNumber`, which reads the locale to pick its decimal separator, and `Counter`, which wraps it). A missing provider does not fail typecheck: `client:visible` still renders on the server, so it throws during prerender and fails the build, in the other workflow. Both cost nothing where unused: `LazyMotion` with `domAnimation` is lazy by construction and `NextIntlClientProvider` with empty messages is inert.
- **A `pre` a component renders itself gets none of Expressive Code's chrome, overflow included**: only a markdown fence goes through Expressive Code. The rule in [`src/styles/global.css`](./src/styles/global.css) gives any such block (`StrategyRanking`'s is one) `overflow-x` and `min-width: 0`: the content column is a grid item, so without the second the block's min-content width becomes the column's and one long line pushes the whole page sideways on a phone.
- **The app styles this site takes arrive through [`src/styles/global.css`](./src/styles/global.css), in an order that is deliberate, and never through [`apps/web/src/ui/styles/index.css`](../web/src/ui/styles/index.css)**, which carries the full `tailwindcss` and the app's layers. The app theme comes first, so its `@custom-variant`s exist before `@astrojs/starlight-tailwind` redeclares `dark` (root and descendants, a superset of the app's descendants-only variant) and wins. Tailwind's theme and utilities follow *without* preflight, because Starlight owns the base styles and importing `tailwindcss` wholesale would double it. The `@layer base, starlight, theme, components, utilities;` statement at the top reads as if it could go, since the emitted bundle carries only `@layer starlight,theme,components;`: Lightning CSS prunes the names it already sees declared in the right position, and the first appearances that ship are `base`, that statement, then `utilities`. Delete it and the `@theme` variables land unlayered and the order becomes base, utilities, theme, starlight, so Starlight outranks the app's own utilities.

## Conventions

- Variant tables are typed `Record`s over `VariantProps<typeof xxxVariants>`, and token values render through the runtime visualizers (`TokenSwatch`, `ShadowScale`, `TypeSpecimen`). Prop tables go through [`src/components/PropsTable.tsx`](./src/components/PropsTable.tsx): a component demo exports `X_PROP_ROWS` built with `propRows<OwnProps<ComponentProps<typeof X>, Base>>`, where `OwnProps` is the component's keys minus the element or primitive it wraps, or with `propRows<keyof ComponentProps<typeof X>>` when it wraps none, so the `Record` is exhaustive over exactly the props the app adds and a prop the app adds, renames or removes fails `astro check` until its row is written. Where the delta is not a clean set (a component whose props are an intersection with Motion's, or a Base UI root passed through untouched) the rows are untyped and list the props worth knowing, so nothing checks their names or their defaults against the component; the page says which base the rest are forwarded to.
- **Every chrome rule in `global.css` reads the app's tokens** (`--frame`, `--accent`, `--surface-panel-*`, `--shadow-brutal-*`), so the wiki re-themes with the app and flips with `data-theme` as it does; Starlight's defaults are soft and rounded, the app's are hard frames and offset shadows. The `@theme` block maps the brand onto Starlight's chrome, and `starlight-tailwind` wires its accent and gray scales into the `--sl-color-*` properties. The `[data-slot]` transition block is a scoped copy of the app's `base/index.css`, which cannot be imported wholesale, so demoed components keep their colour and filter easing.
- **The rules in `global.css` each answer a failure**:
  - Starlight renders a table as `display: block` so it can scroll, which stops it filling the column, so a table is `display: table` at full width and wraps long cells with `overflow-wrap: break-word`, never `anywhere`: `anywhere` counts toward a column's minimum width, so a narrow column collapses to one character per line. A header cell stays on one line. Below the sidebar breakpoint the table goes back to Starlight's scrolling block, because a wide table cannot fill a narrow column honestly.
  - The generated tables (props, variants, tunables, strategies) pin their columns with a `colgroup`, and only there is the eager break wanted: in a fixed layout a token that does not fit has nowhere else to go, while a long identifier anywhere else sets its column's minimum width and squeezes the prose beside it. Their `code` is tighter than prose code, because the default chrome's padding pushed a nine-character token past its pinned column.
  - A card lifts on hover with `translate`, never `transform`: `CardGrid`'s stagger positions the second column with a transform, and a hover transform would replace it.
  - The minimal link button gets its inline padding back, because Starlight zeroes it and a framed button then reads as clipped.
  - The slice of preflight the demos depend on is scoped to `.not-content` and written inside `@layer base`. The app's components assume Tailwind's preflight, which this site does not import, so without it a `ghost` Button keeps the browser's grey and every form control renders in the user-agent font; scoping keeps Starlight's own chrome unchanged, and the layer keeps a `bg-*` utility winning, where unlayered rules would flatten every filled Button.
- **[`astro.config.ts`](./astro.config.ts) hands Vite an inline, empty PostCSS config.** Tailwind runs through its Vite plugin, and without the override Vite walks up from this package and loads the app's `postcss.config.mjs`.
- **[`HitAreaDemo.tsx`](./src/components/demos/HitAreaDemo.tsx) writes a plain `<button>` on purpose.** It has the app Button's recipe (border, brutal shadow, hover lift) without the `hit-area-stable` utility, to reproduce the hover flicker the utility removes; do not replace it with `Button`.
- **Mermaid fences are drawn at build time.** Starlight runs on Sätteri, Astro's default Markdown processor, which takes mdast plugins rather than remark ones: [`src/lib/mermaid-plugin.ts`](./src/lib/mermaid-plugin.ts) replaces every ```mermaid fence with two `<figure>` elements, one per theme, and `astro.config.ts` hands the plugin to `satteri({ mdastPlugins })` as `markdown.processor`, which the MDX integration inherits. [`src/lib/mermaid-render.ts`](./src/lib/mermaid-render.ts) does the drawing in one headless Chromium held open for the whole build (the `@playwright/test` the suite already needs), with the site's own body face loaded so labels are measured against the glyphs a reader will see, and with the palette read out of the app's [`global/index.css`](../web/src/ui/styles/global/index.css) rather than spelled a second time, so a token the sheet stops declaring fails the build by name; the dark block restates only what changes, so a token missing there falls back to `:root`. Results are memoised by content hash, so a diagram repeated across locales is drawn once.

  **The layout engine is pinned to dagre in the renderer's config**, because Mermaid 12 makes ELK the default for flowcharts and state diagrams and a bump would otherwise re-lay out every diagram on the site; a fence's own frontmatter outranks the config, so the contract suite fails a fence that sets another layout.

  Four details are load-bearing. **A source Mermaid cannot parse fails the build**, naming the page, rather than shipping a frame that reads `error` in the browser. **Labels are SVG text, not `<foreignObject>` HTML** (`htmlLabels: false`): the HTML kind is measured against a page stylesheet this renderer does not have, which scrambles the layout, and HTML inside the SVG is what makes the two copies nest. **The two figures are emitted as two nodes** through `context.replaceNode(node, [light, dark])`, not as one string holding both, for the same nesting reason. **The theme is picked in CSS**, by `figure.mermaid-dark`/`-light` rules keyed on `data-theme` with a `prefers-color-scheme` middle state, because Starlight's own `dark:sl-hidden` utility is layered and the frame's own `display: flex` outranks it.

  The client script, [`src/lib/mermaid.ts`](./src/lib/mermaid.ts), is a click-to-enlarge toggle and nothing else: no Mermaid reaches the browser, there is no flash of source text before a draw, and a reader without JavaScript sees the diagram. The source rides along URI-encoded in `data-mermaid` for anyone reading the markup. Do not move the drawing to the browser: that costs a visible rehydration on every page and a megabyte of Mermaid in the bundle.
- Demos live in [`src/components/demos/`](./src/components/demos), wrapped in `<Demo>` and hydrated with `client:visible`. `Demo` renders a *Live · apps/web* chip **outside** the `data-demo` frame, deliberately: the demos suite counts that frame's children, and a chip inside it would let a demo that renders nothing pass as rendered.
- A component page's `## In the app` section cites the feature modules that import the component as file names, which the contract suite resolves; `## Accessibility` says what Base UI wires and what the caller owes.
- **`Demo` marks its frame with `data-demo`, and [`e2e/demos.spec.ts`](./e2e/demos.spec.ts) walks every page that carries one.** The list is derived from `dist/**/index.html` after the build, not from the MDX sources: a page that names `components/demos/` in prose, or imports a plain constant like `APP_LOCALES`, renders no demo. One test per page plus a floor assertion, so a build that stops emitting demos fails rather than passing with an empty list; the floor is in the spec. Each page answers 200, every `data-demo` frame has at least one element child once scrolled into view, every island has hydrated (no `astro-island[ssr]` is left, then two frames for React to commit), and the page raises no `pageerror` and logs no `console.error`. That last one is the point: **a demo can break in the browser and build green.** The wait for hydration is what makes it deterministic: a hydration mismatch (React error #418, such as a `div` inside a `<p>`) is raised only once the island hydrates, and an assertion that runs before then passes or fails on timing. Text is no signal: an `Input` or `Slider` demo renders none.

  **Playwright collects every spec before it applies `--grep`**, so a spec that reads `dist/` while being collected breaks the smoke job, which has no build. `demos.spec.ts` derives an empty page list and skips its floor when `BASE_URL` is set, so it stays a local-build suite.

  **`test:e2e` does not build, and it needs the build.** `astro preview` serves `dist`, it does not produce it, and the page list is read off `dist` while the spec file is being collected. [`playwright.config.ts`](./playwright.config.ts) checks for `dist` when it loads, before the web server starts and before any spec is collected, and throws a message naming the build command; with `BASE_URL` set it skips that check and the web server. CI builds first, so the script does not.

  **Under a coding agent, `astro preview` puts itself in the background**, because Astro routes the command through `am-i-vibing` and switches to a daemon plus JSON logs when it detects one. The foreground process then exits at once and Playwright reports `Process from config.webServer exited early`. Run it a second time, which reuses the daemon, or `pnpm exec astro preview stop` first. A stale daemon started before a rebuild serves the previous HTML against the new assets, which shows up as a hydration error on one page and nothing else. CI is unaffected: no agent is detected there, so the server stays in the foreground.
- Content lives in [`src/content/docs/`](./src/content/docs) (root locale = English, pathless URLs). `es/` mirrors filenames; untranslated pages fall back to English automatically. `ca`, `it`, `fr` and `de` are declared in `astro.config.ts` with no folder of their own, so every page falls back to English there and only Starlight's chrome and the sidebar group labels are translated. Sidebar order via `sidebar.order` frontmatter. **A page states the present and history stays in git** (`G8`): the contract suite fails `used to`, `no longer`, `previously`, `any more`, `until now` and a dated event in the prose of a page, outside code and quotes, so a correction rewrites the sentence instead of narrating the one it replaces.
- Formatting and linting: the root Biome config, which formats and lints every file in this package, [`src/styles`](./src/styles) included; `lint-staged` calls the root script. No Prettier. **This package carries no Biome scripts of its own**: its scripts are `dev`, `build`, `preview`, `deploy`, `upload`, `typecheck` and `test:e2e`, and `docs.yml` runs `typecheck`, `build` and `test:e2e`.
- **[`src/content/i18n/es.json`](./src/content/i18n/es.json) holds only strings this site really changes**, all shortenings that fit the chrome, since Starlight ships its own Spanish bundle; the contract suite fails on a key identical to the vendor's, and on a `search.ctrlKey` that is more than a modifier, because Starlight renders the `K` beside it itself.
- "Design system" stays English in every locale on purpose: each of its sidebar translations restates the label.

## Analytics and consent

The wiki measures itself, and everything it measures is browser-side. There is no observability here and there
cannot be: `wrangler.toml` declares no `main`, so Cloudflare serves the built assets without invoking a script
and there is no handler, `fetch` or binding call to trace. Naming a `destinations` entry would create a
destination that receives its own test message and nothing else.
[ADR 0019](../../adr/0019-the-wiki-measures-itself-with-its-own-consent-flow.md) records the whole decision.

- [`src/lib/analytics/consent.ts`](./src/lib/analytics/consent.ts) configures `vanilla-cookieconsent` with the
  library's own UI, in every locale the site serves, picked off `document.documentElement.lang`, and wires the
  answer to both services. [`src/components/Head.astro`](./src/components/Head.astro) is a Starlight `Head` override
  that emits Consent Mode defaults of `denied` before `gtag.js` loads, then boots the consent module and the
  diagram zoom.
- **This shares the library and the vocabulary with the app, and nothing else.** The `analytics` category and
  the `ga4` and `betterStack` service ids are the same strings, and `vanilla-cookieconsent` is pinned to the
  same version, so a reader can move between the two. The answers both banners give (accept all, reject all, the
  preferences title, close) use the app's words in each locale. The contract suite compares the ids with the
  app's `cookie-consent/utils/consent.ts`, the banner's locales with the ones `astro.config.ts` serves, and those
  words with the app's bundles. The app's consent UI is React reading `next-intl` off its own bundles,
  with a cookie table listing Stripe cookies the wiki never sets; porting that into an island would cost more
  than the file it replaces.
- **Google Analytics uses the app's measurement id on purpose.** Both sites are subdomains of
  `forever-pto.com`, so one id gives a single session that runs from the wiki into the planner, separated by
  the `Hostname` dimension. It lives in one repository variable, `GOOGLE_ANALYTICS_ID`, and each workflow maps
  it to the prefix its bundler inlines.
- **Better Stack RUM uses a source of its own, per stage, under one variable name.** Sharing the app's would
  file wiki sessions under the app's `release`, and this tag passes no `release` of its own at all. So
  `BETTER_STACK_TRACKING_TOKEN` is a variable on `docs-development` and `docs-production`.
- **Which is why `build` in [`docs.yml`](../../.github/workflows/docs.yml) declares an `environment:`.** A job
  without one reads an empty string from any environment variable, and the single `docs-dist` artifact both
  `preview` and `deploy` ship can only carry one baked value. The job names `docs-development` on a pull
  request and `docs-production` otherwise, so each build takes its own stage's token. If `docs-production` ever
  grows a required reviewer, that gate moves onto the build.
- **The tags report a floor, not a census.** Better Stack RUM is Sentry's browser SDK underneath and posts to
  a Sentry `envelope` endpoint, which ad blockers filter hard; GA4 fares no better. Only Cloudflare's own
  request analytics cannot be blocked. `blocked:other` on that POST in DevTools is an extension, not the CSP:
  `_headers` admits the host.
- **[`public/_headers`](./public/_headers) carries the CSP that admits the two tags**, plus HSTS, `nosniff`,
  `DENY` framing, a referrer policy, a permissions policy and a `same-origin` opener policy. The app states
  its own policy in `next.config.ts`, which the contract suite asserts; this one has no Worker to serve it
  from, so Cloudflare's static-asset `_headers` support is what applies it. Nothing compares the two.
- **Two of its directives look loose and are load-bearing.** Pagefind, which Starlight's search box runs on,
  compiles a WebAssembly module in the browser, and a `script-src` without `'wasm-unsafe-eval'` refuses to
  instantiate it: the dialog opens, the input accepts typing and it says *Searching for …* forever, because
  the only symptom is a console `CompileError`. `font-src 'self' data:` is the other: Vite inlines the smallest
  `@fontsource` subset as a `data:` URI, so `'self'` alone blocks one JetBrains Mono face and the mono text
  falls back to the UA font on some pages and not others. `'wasm-unsafe-eval'` grants WebAssembly and nothing
  of what `'unsafe-eval'` would. Cloudflare's own `static.cloudflareinsights.com` beacon stays blocked on
  purpose: the site already carries GA4 and Better Stack RUM.
- **[`e2e/cookie-consent.spec.ts`](./e2e/cookie-consent.spec.ts) has to tell the browser it is not a robot.**
  `vanilla-cookieconsent` defaults `hideFromBots` to true, and the check is
  `/bot|crawl|spider|slurp|teoma/i.test(userAgent) || navigator.webdriver`. Playwright sets
  `navigator.webdriver`, so the banner never renders while `run()` resolves without an error, which reads as
  broken code and is the library doing its job. The spec overrides that property in a `beforeEach`. Two of its cases read the Consent Mode calls that `Head.astro`
  writes only when `PUBLIC_GOOGLE_ANALYTICS_ID` is set at build time, so they fail against a local build
  without it ([`.env.example`](./.env.example) names both variables); the Docs workflow sets it.

## Deploy

Wrangler environments, the same shape the app uses. `[assets]` is declared once at the top level and both inherit it. **`name` does not differ between the top level and production**: both are `forever-pto-docs`, and what production actually overrides is the route plus the exposure flags.

- **main**: `deploy --env production` → `forever-pto-docs`, bound to docs.forever-pto.com. The route is `custom_domain = true`, so wrangler provisions the DNS record and the certificate in the forever-pto.com zone itself; there is nothing to configure in the dashboard.
- **PRs**: `deploy --env development --name pr-<n>-forever-pto-docs-development` → one Worker per pull request at `pr-<n>-forever-pto-docs-development.fbuireu.workers.dev`. The `--name` override is what mints a fresh Worker instead of updating the stable one, so open PRs never overwrite each other's preview.
- **[`cleanup-development.yml`](../../.github/workflows/cleanup-development.yml) deletes it when the PR closes**, in a job of its own beside the app's. A per-PR Worker that nothing tears down accumulates forever.
- **Previews never touch the production Worker**, which is the whole point of the development environment: it carries no custom domain, so a preview cannot answer on docs.forever-pto.com.
- The GitHub environments are split per package: this site uses `docs-production` and `docs-development`, and carries none of the app's `NEXT_PUBLIC_*` values in either. What it does carry on both is `BETTER_STACK_TRACKING_TOKEN`, read by `build` rather than by a deploy job; see *Analytics and consent*. The jobs that call Cloudflare (`preview`, `deploy` and `rollback` in `docs.yml`, `cleanup-docs` in `cleanup-development.yml`) each declare `environment:` and read `CLOUDFLARE_API_TOKEN` from inside it, so both `docs-*` environments carry the Cloudflare pair, as the root guide's *CI* section lists. Only `PAT` and `CODECOV_TOKEN` are repository-level.
- **`workers_dev` and `preview_urls` are inheritable, so production has to refuse them explicitly.** Both are `true` at the top level, which is what a per-PR preview needs and what `[env.development]` therefore inherits rather than restating, and `[env.production]` sets both to `false`; inherited, they would put the published wiki on a `workers.dev` origin too.
- **`pnpm --filter forever-pto-docs deploy` passes no `--env`, so it deploys the top-level config to the live production Worker.** The top level carries production's own `name` with no route block and with `workers_dev = true`, so a local one-shot deploy overwrites docs.forever-pto.com and turns its `workers.dev` origin back on. Run `wrangler deploy --env production`, which is what the workflow runs.
