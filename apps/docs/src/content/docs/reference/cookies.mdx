The app sets its first-party cookies. The sidebar cookie name below is imported from the app source, so it cannot drift; the other names are set in infrastructure modules (not importable into this site) and are quoted as written in code, with the defining file cited.

| Cookie | Purpose | httpOnly | Secure | SameSite | Max age |
| --- | --- | --- | --- | --- | --- |
| `user-country` | Detected ISO country code, used to pre-select the holiday calendar | no | yes | `strict` | 7 days (`ONE_WEEK`) |
| `NEXT_LOCALE` | The user's resolved locale for i18n routing | no | yes | `lax` | session |
| `premium-token` | JWT proving an active premium session | yes | production only | `strict` | 30 days |
| `premium-activation` | One-shot proof that a payment just activated Premium and nobody has reported it yet | no | production only | `strict` | 1 hour |
| <code>{SIDEBAR_COOKIE_NAME}</code> | Persists whether the sidebar is expanded or collapsed | no | not set | `lax` | 7 days |

All of them are scoped to `path: '/'`.

## `user-country`

Exported as `USER_COUNTRY_COOKIE` in `apps/web/src/infrastructure/proxy/cookie.ts`, which also defines `setLocationCookie()` and the attributes above. It is written by the proxy chain: `apps/web/src/middleware.ts` → `apps/web/src/infrastructure/proxy/location.ts`, which detects the country from the request and sets the cookie on the response. It is deliberately **not** `httpOnly`, because `apps/web/src/ui/modules/stores/StoresInitializer.tsx` reads it on the client to seed the location store. See [country detection](/how-it-works/country-detection/).

## `NEXT_LOCALE`

The locale cookie used by next-intl, named by the `LOCALE_COOKIE` export in `apps/web/src/infrastructure/i18n/locales.ts`. The next-intl middleware sets it during locale negotiation, and `apps/web/src/middleware.ts` immediately re-sets it via `setLocaleCookie()` (`apps/web/src/infrastructure/i18n/cookie.ts`), which applies `LOCALE_COOKIE_POLICY`: `secure`, `sameSite: 'lax'`, `path: '/'`. No `maxAge` is set, so it is a session cookie.

It is deliberately **not** `httpOnly`, and that is the same object `routing.ts` hands next-intl. The client-side language switcher writes this cookie too, from `document.cookie`, so both writers have to agree: adding `httpOnly` here silently broke every soft locale switch.

## `premium-token`

Named by the `PREMIUM_COOKIE` export in `apps/web/src/infrastructure/services/premium/cookie.ts`. `setPremiumCookie()` stores the signed JWT after a successful premium activation, with `secure` enabled only when `NODE_ENV` is `production` (so it works over plain HTTP in local dev). The session duration constant in the same file is 30 days. It is read and refreshed (or cleared via `clearPremiumCookie()`) by `apps/web/src/app/api/check-session/route.ts`.

## `premium-activation`

Named by the `ACTIVATION_COOKIE` export in `apps/web/src/application/dto/payment/types.ts`, so the route that sets it and the browser code that spends it share one name. `setActivationCookie()` in `apps/web/src/infrastructure/services/premium/cookie.ts` sets it beside `premium-token` when `GET /api/payment/activate` grants Premium, for `ACTIVATION_PROOF_LIFETIME_SECONDS`, with the value `1`: it carries no identifier and grants nothing. The premium store's `confirmActivation` reads it once the session check answers with a session, deletes it in the same task and reports `premium_activated` only when it was there, through `claimActivationProof()` in `apps/web/src/ui/adapters/session/checkSession.ts`. It is deliberately **not** `httpOnly`: a proof only the server could spend would need a request to spend it, and a reload between the server spending it and the page reading the answer would lose the report. See [premium](/how-it-works/premium/).

## <code>{SIDEBAR_COOKIE_NAME}</code>

The only client-set cookie in the table. `apps/web/src/ui/utils/sidebarCookie.ts` declares `SIDEBAR_COOKIE_NAME` (interpolated on this page) and `SIDEBAR_COOKIE_MAX_AGE`, 7 days, and nothing else, so the consent catalogue reads the name without loading the sidebar; `apps/web/src/ui/modules/core/animate/base/Sidebar.tsx` writes `true`/`false` under them through the `setCookie()` helper in `apps/web/src/ui/utils/cookie.ts`, which uses the CookieStore API with a `sameSite: 'lax'` default. Being set from the browser it cannot be `httpOnly`.

## Third-party cookies

Cookies set by Stripe, Google Analytics and Better Stack are not controlled by app code. They are catalogued, with names, providers and expiries, in `apps/web/src/ui/modules/shared/cookie-consent/config/config.ts`, which drives the cookie-consent dialog. The same catalogue lists every cookie in the table above, under the provider Forever PTO and by the constant the code writes it by, and the contract suite fails a cookie the code writes that it leaves out.
