All workflows live in `.github/workflows/`. Two repo-wide conventions, enforced socially and by zizmor: every third-party action is SHA-pinned (with a version comment), and every checkout uses `persist-credentials: false`.

| Workflow | Trigger | Purpose |
| --- | --- | --- |
| `ci.yml` | push to `main`, PRs to `main` | The whole app graph: change detection, one `Check` job running `pnpm verify`, both deploys, the E2E run and the web release |
| `_deploy-web.yml` | `workflow_call` | Reusable OpenNext build + deploy + secret push |
| `cleanup-development.yml` | PR closed | Delete the per-PR preview Worker |
| `docs.yml` | push / PR touching `apps/docs/**` | This site's build, checks and deploy |
| `zizmor.yml` | push to `main`, all PRs | Workflow security linting |
| `dependency-review.yml` | all PRs | Fails a PR that introduces a dependency with a known vulnerability |
| `commit-message.yml` | PR opened/edited/reopened/synchronize | commitlint on the **pull request title**, the string a squash merge commits |
| `renovate-auto-approve.yml` | Renovate PRs (by label) | Auto-approve safe dependency PRs |
| `dependabot-auto-merge.yml` | Dependabot PRs | Fires for security updates; Renovate handles version updates |

## `ci.yml`: CI

Runs on pushes to `main` and PRs targeting `main`. `cancel-in-progress` is conditional on `pull_request`: cancelling a superseded PR run is free, cancelling a `main` run would kill a deploy or a release halfway.

- **changes**: derives from `git diff` whether `apps/web` (or anything the app build depends on) was touched, and exposes it as an output. It uses `git diff` rather than a filter action because every third-party action here is SHA-pinned and an unpinnable one trips zizmor. It fails open.
- **Check**, one job running `pnpm verify`: `format:check` (Biome, no writes), `typecheck` (the root program, then `apps/web`, then `astro check` over `apps/docs`) and `test:ut:coverage` (`apps/web`'s Vitest run, then the contract suite), then coverage upload to Codecov from `apps/web/coverage/lcov.info` (`fail_ci_if_error: false`, so Codecov outages never block CI). The same command is what `pre-push` runs, so a green push is a green CI.
- **deploy-production → smoke → release-web → docs-refresh** on `main`, with **smoke → rollback** when the smoke run fails, or **deploy-development → comment / e2e** on a PR. `deploy-tail` and `cross-package-notice` hang off `changes` on their own conditions.
- **smoke**: the only job that requests `https://forever-pto.com` itself. `e2e` runs against a per-PR preview and only on `pull_request`, so before this job a push to `main` deployed production and cut a tag without a single request to the live site. It runs Playwright with `--grep "@smoke"`, no Cloudflare Access headers (production is public) and no `environment:` of its own. Three cases carry the tag and all live in `apps/web/e2e/smoke.spec.ts`: the homepage, the 404 route and `robots.txt`. It is the same trio every sibling repository runs, so a difference between them is drift. They are kept in one file because a failing smoke case rolls production back, so the set that holds that power has to be readable in one place. `/sitemap.xml` and `/api/health` were in the set and are not any more: they answer 403 to a GitHub runner while a browser gets the expected response, so on 2026-08-29 they reverted a deploy that was fine. A case whose result depends on the caller's address is evidence about the caller, not about the deploy. The step passes no `--pass-with-no-tests` on purpose, so a grep that stops matching fails rather than passing quietly, and `release-web` needs this job as well as the deploy, so a tag means the version is live and answering.
- **rollback**: runs `wrangler rollback --env production` from `apps/web` when the deploy succeeded and `smoke` failed, so a version that does not answer stops serving rather than only going untagged. Unlike `smoke` it declares `environment: web-production`, because rolling back needs the Cloudflare credentials.

`Check` is what the ruleset gates PRs on, and it gates *deploying* too: `deploy-production` `needs: [changes, check]` and `release-web` `needs` the deploy, so a tag means the version is live. `Check` runs unconditionally, because the contract suite reads `CONTEXT.md`, `adr/` and every guide, so a markdown-only change must not slip past it; only the deploy and release jobs consult `changes`. Package scoping uses step-level `working-directory`, because a job-level default would not reach a `uses:` step, which is why the two `nick-fields/retry` commands left in the tree, both in `cleanup-development.yml`, begin with an explicit `cd`.

## `_deploy-web.yml`: Deploy web (reusable)

A `workflow_call` workflow shared by both deploy entry points. Inputs: `environment` (GitHub environment name), `wrangler_env` (`--env` for wrangler), optional `url` (shown on the PR/deployments UI) and optional `worker_name` (the per-PR override). Steps:

1. Install deps, then build with `pnpm run cf:build` (OpenNext). The build step receives the `NEXT_PUBLIC_*` GitHub environment *variables*. These are baked into the client bundle at build time. It is a plain `run:` step: a build fails deterministically, so wrapping it in `nick-fields/retry` only burned three identical attempts before reporting the same type error.
2. A Node guard fails the job if any of the five runtime secrets is missing, rather than deploying a half-configured Worker, and writes them as JSON to a file under `$RUNNER_TEMP`. See [secrets](/infra/secrets/).
3. `pnpm exec wrangler deploy --env <wrangler_env> --secrets-file <file>`, adding `--name <worker_name>` when set; the name override is what creates a fresh per-PR Worker. The secrets ride the deploy, so they land on the same Worker version as the code that reads them, where a separate `wrangler secret bulk` call made a second version and left a window in which the new code ran against the old values.
4. An `if: always()` step removes the file.

### The deploy jobs

`deploy-development` calls `_deploy-web.yml` with the `pr-<n>-forever-pto-development` name override, then `comment` upserts a sticky preview-URL comment keyed on a hidden HTML marker and `e2e` runs Playwright chromium against the live preview through a Cloudflare Access service token, uploading its report as an artifact. The workflow's concurrency group cancels in progress on a `pull_request` event only, so rapid pushes deploy just the latest commit while a `main` run is never killed halfway. The full lifecycle is on the [environments](/infra/environments/) page.

`ci.yml` also answers `workflow_dispatch`: a manual dispatch on `main` runs `deploy-tail` unconditionally, which is how the tail Worker picks up a rotated BetterStack token or host — those are read at deploy time, so rotating the variables changes no file and matches no path filter. The push-triggered jobs keep their gates.

`deploy-production` calls the same reusable workflow with `environment: web-production`, `wrangler_env: production` and `url: https://forever-pto.com`, and no `worker_name` override, so it updates the `forever-pto` Worker in place. It `needs: [changes, check]`, so a red `main` does not ship and a docs-only commit does not redeploy. See [release](/infra/release/).

## `cleanup-development.yml`: Cleanup - Development

On `pull_request: closed`, two jobs: `cleanup-web` deletes `pr-<n>-forever-pto-development` and `cleanup-docs` deletes `pr-<n>-forever-pto-docs-development`, both through `nick-fields/retry` wrapping `pnpm exec wrangler delete --force`. That is the one place the retry wrapper is still right: the call is idempotent, its argument is a name the workflow composes rather than a flag, and it already treats *does not exist* as success. Shared dev R2/KV/Turso state is intentionally left alone.

Each job declares its **own** group, with `cancel-in-progress: false`, naming the workflow that deployed the Worker it deletes: `CI-${{ github.ref }}` for `cleanup-web`, `docs-${{ github.ref }}` for `cleanup-docs`. That is what stops a delete landing on a Worker a job is still driving. One workflow-level group used to cover both, which queued `cleanup-docs` behind `ci.yml` while its Worker belongs to `docs.yml`; see [environments](/infra/environments/).

## `docs.yml`: Docs

CI/CD for this documentation site, path-filtered to `apps/docs/**` plus everything the site reaches into the app for: `apps/web/src/ui/**`, `apps/web/package.json` (the version the site displays), `apps/web/src/domain/calendar/types.ts` and `apps/web/src/infrastructure/i18n/locales.ts`. It also answers `workflow_dispatch`, which is how `ci.yml`'s `docs-refresh` job rebuilds the site after a web release: the release commit carries `[skip ci]`, so without the dispatch the published site keeps advertising the previous version. It also carries `release-docs`, which runs after the docs deploy **and** its `smoke` job, so a `docs-v*` tag only exists once the site is live and answering, and `rollback`, which reverts the Worker when that smoke run fails. Build & test, versioned PR previews and production deploy of the `forever-pto-docs` Worker; the full walkthrough is on [docs CI](/infra/docs-ci/).

## `commit-message.yml`: Commit Message

Runs commitlint on the **pull request title**, not on the branch's commits. `main` takes squash merges and the repository sets the squash title to `PR_TITLE`, so that title is the message that lands and the one semantic-release parses. The `commit-msg` hook validates commits the squash then discards, which makes this the only guard on the string that ships, and GitHub pre-fills the title from the *branch name* whenever a PR carries more than one commit, so the default is rarely conventional.

It re-runs on `synchronize` even though a push cannot change the title: required status checks are evaluated against the head SHA, so without it a new commit would leave the check unreported and block the PR.

## `dependency-review.yml`: Dependency Review

Fails a PR that introduces a dependency with a known vulnerability, reading the lockfile diff. Runs on every PR and needs no secrets.

## `zizmor.yml`: Security Analysis with zizmor

Runs the zizmor GitHub Actions security linter on pushes to `main` and every PR, reporting to GitHub code scanning (`security-events: write` is its only permission). This is what makes the SHA-pinning and `persist-credentials: false` conventions stick: any new workflow (including docs ones) gets linted too.

## `renovate-auto-approve.yml`

Approves Renovate PRs so their automerge can proceed. Gated on the PR author being `renovate[bot]` *and* carrying one of the labels Renovate adds by update type (`patch-update`, `minor-update`, `pin-update`, `lock-maintenance`). It checks for an existing approval first, then `gh pr review --approve` with the `PAT` secret. See [Renovate](/infra/renovate/).

## `dependabot-auto-merge.yml`

Approves and auto-squash-merges Dependabot patch, minor and dev-dependency PRs, and labels them by update type. **It is not dormant.** There is no `.github/dependabot.yml`, so Dependabot opens no version-update PRs here, which is Renovate's job. But the **security** updates GitHub raises from its own vulnerability alerts need no config file, they arrive as `dependabot[bot]`, and `fetch-metadata` reports them with the same `version-update:semver-patch` and `-minor` types the auto-merge branch accepts. So the guard does match, and this is the repository's only unattended auto-merge path: it runs `gh pr review --approve` and `gh pr merge --auto --squash` under `secrets.PAT`. Do not read it as safe to ignore.
