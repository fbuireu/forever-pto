There are three distinct classes of configuration, and each has exactly one home. Mixing them up is the main way deploys break.

| Class | Lives in | Reaches the app as |
| --- | --- | --- |
| Build-time public vars (`NEXT_PUBLIC_*` tokens/ids) | GitHub environment **variables** | Baked into the client bundle by `cf:build` |
| Runtime secrets | GitHub environment **secrets** → `wrangler deploy --secrets-file` | Worker-attached secrets (`process.env` at runtime) |
| Non-secret runtime vars | `[vars]` / `[env.*.vars]` in `wrangler.toml` | Worker vars, committed and versioned |

## GitHub environments

Four GitHub environments (`web-production`, `web-development`, `docs-production` and `docs-development`) hold the per-environment values. They are split per package so a docs deploy does not pass through whatever gate protects web production, and so the app's `NEXT_PUBLIC_*` variables are not visible to jobs that have no use for them. Only the two `web-*` environments carry those values:

- **Variables** (`vars.*`): the `NEXT_PUBLIC_*` values (Better Stack tokens, Stripe publishable key, GA id, storage key) that `_deploy-web.yml` injects into the build step. Being `NEXT_PUBLIC_*`, they end up in the public client bundle; they are *configuration*, not secrets, but still per-environment. Two of them are also handed to the Worker at deploy time under the names the tail Worker reads, because the tracing wrapper runs before Next and cannot see the inlined build values: `NEXT_PUBLIC_BETTER_STACK_INGESTING_URL` as the `BETTER_STACK_INGESTING_URL` var, and `NEXT_PUBLIC_BETTER_STACK_SOURCE_TOKEN` inside the secrets file as `BETTER_STACK_SOURCE_TOKEN`. The deploy fails before uploading anything when either is empty.
- **Secrets**: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, and the five runtime secrets below, plus `CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET` for the E2E job. Repo-level secrets also include `PAT` (releases and bot approvals) and `CODECOV_TOKEN`.

This documentation site needs none of the app's `NEXT_PUBLIC_*` values, but `docs-production` and `docs-development` are not empty: `docs.yml`'s deploy and preview jobs and `cleanup-development.yml`'s docs cleanup all declare `environment:` and all read `CLOUDFLARE_API_TOKEN` from inside it. Only `PAT` and `CODECOV_TOKEN` are repository-level. A job naming an environment that does not carry the Cloudflare credentials gets an empty string, wrangler falls back to interactive OAuth, opens a browser on a headless runner and times out after 120 seconds per attempt, so the credentials have to be copied onto all four (see [docs CI](/infra/docs-ci/) and the repository guide's setup checklist).

## Runtime secrets: uploaded with the version

The five runtime secrets (`JWT_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `RESEND_API_KEY`, `TURSO_AUTH_TOKEN`) are **re-uploaded on every deploy**, by the deploy itself, in `.github/workflows/_deploy-web.yml`:

1. A Node one-liner validates that all five are present, failing the job before anything is deployed, and writes them as JSON to a file under `$RUNNER_TEMP` at mode `600`. Deliberately not inside the workspace: nothing an `upload-artifact` step globs can reach it there.
2. `pnpm exec wrangler deploy` takes that file on `--secrets-file`, so the secrets land on the **same Worker version** as the code that reads them.
3. An `if: always()` step removes the file.

It used to be a separate `wrangler secret bulk` call *after* the deploy, and the ordering was forced rather than chosen: a secret write needs the Worker to already exist, so pushing first fails a new per-PR Worker with `script_not_found [code: 10007]`. The cost was that every deploy produced two Worker versions, and in the window between them the new code ran against the previous deploy's secret values. `--secrets-file` removes the second call instead of reordering it.

`--secrets-file` is additive exactly as `secret bulk` was: a key the file omits is not deleted. Re-uploading every time still makes deploys idempotent, so rotating a secret is "update the GitHub environment secret, redeploy". Preview Workers take their secrets to the grave when [cleanup deletes them](/infra/environments/).

## Local development

- `.dev.vars` (gitignored) holds the local equivalents of the Worker secrets; wrangler and `initOpenNextCloudflareForDev()` pick it up automatically. `.env.example` documents the expected keys.
- **Never commit `.env` files.** `.gitignore` carries `.env*` with `!.env.example`, and `git log --diff-filter=A` finds no `.env.development` or `.env.production` in any branch's history: the two files sitting at `apps/web/` are untracked local copies. This entry used to say the opposite, in the present tense, with a rotate-and-purge follow-up nobody could action.

## Conventions

- New runtime secret? Add it in four places: the two `web-*` GitHub environments, the `secrets:` contract of `_deploy-web.yml` (inputs *and* the `required` list the preflight step checks), `.env.example`, and `environment.d.ts` for typing.
- New public build var? A `web-*` GitHub environment **variable** + the `env:` block of the build step in `_deploy-web.yml`.
- Non-secret, per-environment runtime value (URLs, feature toggles)? `wrangler.toml` vars: committed, reviewed, no ceremony.
