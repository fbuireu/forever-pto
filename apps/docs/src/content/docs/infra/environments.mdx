The app runs as a Cloudflare Worker built with OpenNext. The kinds of environment are all defined by the `[env.*]` blocks in `wrangler.toml`: previews are not a wrangler environment of their own, they are the `development` environment deployed under a different Worker name.

| Environment | Worker | URL | Access |
| --- | --- | --- | --- |
| Production | `forever-pto` | `https://forever-pto.com` (zone route `forever-pto.com/*`) | Public |
| Development (stable) | `forever-pto-development` | `https://forever-pto-development.fbuireu.workers.dev` | Cloudflare Access; deployed by hand only |
| Per-PR preview | `pr-<n>-forever-pto-development` | `https://pr-<n>-forever-pto-development.fbuireu.workers.dev` | Cloudflare Access |

## Production

Deployed by the `deploy-production` job of `.github/workflows/ci.yml` on every push to `main`, gated on the `Verify` job passing and on the `changes` job finding an `apps/web` change, and on a manual `workflow_dispatch` of the same workflow, which is the only way to redeploy it by hand (see [release](/infra/release/) and [workflows](/infra/workflows/)). The Worker is bound to the `forever-pto.com` zone via a route pattern in `wrangler.toml`, a zone route, not a Workers custom domain. It uses the production R2 incremental-cache bucket, the rate-limiter binding and the Turso database (see [Cloudflare stack](/infra/cloudflare/)).

## Development (stable)

The `forever-pto-development` Worker is the long-lived development environment, and **no workflow deploys it**: CI only ever deploys the `development` environment under a `pr-<n>` name. It is updated by hand, from `apps/web`, with `pnpm cf:build` then `pnpm exec wrangler deploy --env development`, which hands off to `opennextjs-cloudflare deploy --env development` like every deploy here, fills the shared development bucket and uploads no secrets, so the Worker keeps the ones it already has. It answers on its `workers.dev` origin, which `wrangler.toml` knows only as the `NEXT_PUBLIC_SITE_URL` var under `[env.development.vars]`; there is no route for it in the file. The whole environment sits behind Cloudflare Zero Trust Access, configured in the dashboard rather than in `wrangler.toml`, so a browser hitting it gets an Access login and CI authenticates with a service token (`CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET`, secrets on the `web-development` GitHub environment).

## Per-PR previews

Every pull request gets its own throwaway Worker.

### Created

The `deploy-development` job of `.github/workflows/ci.yml` fires on `pull_request` (`opened`, `reopened`, `synchronize`) and calls the reusable `.github/workflows/_deploy-web.yml` with `environment: web-development`, from which it derives the wrangler environment `development`, plus a `worker_name` override of `pr-<n>-forever-pto-development`. The `--name` flag on `wrangler deploy` is what mints a brand-new Worker instead of updating the stable one, and `--secrets-file` on the same call is what gives it the five runtime secrets, which do not exist on a Worker until they are uploaded (see [secrets](/infra/secrets/)). After deploying:

1. A sticky PR comment (upserted via a hidden marker) posts the preview URL.
2. A Playwright E2E job runs against the live preview, authenticating through Cloudflare Access with a service token (`CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET`), which `apps/web/e2e/fixtures.ts` adds as `CF-Access-Client-Id/Secret` headers to the requests whose origin is the preview's alone, so no third party the page loads receives it.

### Destroyed

`.github/workflows/cleanup-development.yml` fires on `pull_request: closed` (merged or not) and runs `wrangler delete pr-<n>-forever-pto-development --force`. That single command is the entirety of teardown: the Worker and its attached secrets disappear. It queues behind the pull request's own CI run, in a concurrency group spelled from the pull request number, so the E2E job is never left driving a Worker that no longer exists; a weekly sweep deletes any preview Worker whose pull request is closed, for the cleanups something else lost.

### What survives

Previews deploy with `--env development`, so they all **share** the development bindings: the dev R2 incremental-cache bucket, the rate-limiter binding and the dev Turso database (all declared under `[env.development]` in `wrangler.toml`). None of that state is cleaned up when a PR closes, and one preview's writes are visible to every other preview. Every preview deploy also writes its prerendered pages into that bucket under its own build id, before the Worker is uploaded ([the OpenNext hand-off](/infra/workflows/#what-the-deploy-call-does-the-opennext-hand-off)), and nothing deletes those folders, so the bucket grows by one build per deploy.

```mermaid
  subgraph pr ["Pull request"]

    POP --> C["sticky PR comment with the preview URL"]
    POP --> E["e2e: Playwright through an Access service token"]
  end
  subgraph close ["Pull request closed"]
    X["cleanup-development.yml, queued behind the CI run"] --> DEL["wrangler delete --force"]
    DEL --> GONE["Worker and its secrets gone,<br/>shared dev R2 and Turso untouched"]
  end
  subgraph main ["push to main, or workflow_dispatch"]
    P["changes + Verify"] --> DP["deploy-production"] --> RW2["_deploy-web.yml"]
    RW2 --> W2["wrangler deploy --env production"] --> POP2["pages into the production bucket"]
    POP2 --> LIVE["forever-pto on forever-pto.com/*"]
    LIVE --> SM["smoke, then release-web on a push,<br/>or rollback when it fails"]
  end
  HAND["by hand, from apps/web:<br/>wrangler deploy --env development"] --> STABLE["forever-pto-development"]
```

## The docs site's previews

This documentation site previews the same way, one Worker per pull request named `pr-<n>-forever-pto-docs-development`, deleted by its own `cleanup-docs` job when the pull request closes. What differs is what it does *not* need: no bindings, no `--secrets-file`, no `--var` override, and no second build, since it ships the `docs-dist` artifact the `build` job already produced. See [docs CI](/infra/docs-ci/).
