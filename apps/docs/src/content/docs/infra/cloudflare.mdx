Everything runs on Cloudflare. The account hosts three Workers from this repo, plus storage and access-control services, all on the `forever-pto.com` zone.

## The three Workers

| Worker | Config | What it is |
| --- | --- | --- |
| `forever-pto` (+ `forever-pto-development`, per-PR previews) | `wrangler.toml` | The Next.js app, compiled to a Worker by OpenNext |
| `forever-pto-tail` | `apps/web/workers/tail/wrangler.toml` | Tail Worker forwarding logs to Better Stack |
| `forever-pto-docs` | `apps/docs/wrangler.toml` | This site: pure static assets |

### The app Worker (OpenNext)

`pnpm run cf:build` runs `opennextjs-cloudflare build`, which wraps `next build` and emits `.open-next/worker.js` (the Worker entry in `wrangler.toml`) plus `.open-next/assets` (bound as `ASSETS`). The Worker runs with the `nodejs_compat` compatibility flag family; see `wrangler.toml` for the exact flags and date. Environment split (`[env.development]` / `[env.production]`) is covered on the [environments](/infra/environments/) page.

### The tail Worker

`apps/web/workers/tail/index.ts` implements a `tail()` handler: Cloudflare streams the app Worker's logs and exceptions to it (declared via `[[tail_consumers]]` in every environment of `wrangler.toml`), and it forwards them to Better Stack. It is a separate Worker with its own `wrangler.toml`, deployed by the `deploy-tail` job of `ci.yml`, gated on `TAIL_PATHS`, which covers its own folder plus everything its bundle reaches into, since it rarely changes. The job also passes the ingest host as a `--var` and re-pushes the ingest token, so reissuing the Better Stack source is "update the two variables, rerun the job": neither value is written in `apps/web/workers/tail/wrangler.toml` any more, and the two used to disagree because only the token came from CI. That config declares `[observability]` for the tail Worker itself, so its own invocation logs are retained; a Worker whose job is telling you what happened needs somewhere to say that it could not.

### The docs Worker

`forever-pto-docs` is a static-assets-only Worker (no code, just the Astro `dist/` directory) with a `custom_domain` route for `docs.forever-pto.com` declared in `apps/docs/wrangler.toml`, notably the repo's first infrastructure-as-code custom domain; the app's dev subdomain is dashboard-managed. Deployment is described in [docs CI](/infra/docs-ci/).

## Storage

- **R2: incremental cache.** `open-next.config.ts` wires OpenNext's `incrementalCache` to R2, using the `NEXT_INC_CACHE_R2_BUCKET` binding. Production uses the `forever-pto-next-inc-cache` bucket; development (and every PR preview) shares `forever-pto-next-inc-cache-dev`. This is where ISR/`use cache` output lives between requests.
- **The rate-limiting binding.** `[[ratelimits]]` declares `PAYMENT_RATE_LIMITER` with `simple = { limit = 10, period = 60 }`, once at the top level and again per environment. There is **no KV namespace in this repo**: the counter used to be a read-modify-write over one, which KV cannot make atomic; see [rate limiting](/how-it-works/rate-limiting/).
- **Turso: database.** libSQL over HTTP; one database per environment, configured as the `TURSO_DATABASE_URL` var in `wrangler.toml` with the `TURSO_AUTH_TOKEN` pushed as a [runtime secret](/infra/secrets/). Turso is external to Cloudflare but fits the Worker model (no TCP pooling required).

## Platform features

- **Smart placement.** `[placement] mode = "smart"` lets Cloudflare run the Worker near its backends (the Turso databases) instead of near the user when that lowers total latency, sensible because most requests fan out to the database rather than doing pure edge work.
- **Observability.** Workers Logs and Traces are enabled with invocation logs, head-sampled at the rate set in `wrangler.toml` (the same rate in every environment). Sampled full-fidelity data lives in the Cloudflare dashboard; the tail Worker independently forwards to Better Stack for retention and alerting.
- **Cloudflare Access.** The development Worker and every PR preview sit behind Zero Trust Access, which is why nothing crawls a preview and why `robots.txt` advertising the production sitemap there is tolerated. The Access application is configured **in the Zero Trust dashboard, not in `wrangler.toml`**: this repo carries no team domain, no AUD tag and no JWT validation of its own; Access answers before the Worker runs. CI's Playwright job reaches a preview by sending a service token (`CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET` in `apps/web/playwright.config.ts`); see [environments](/infra/environments/).
- **That protection covers two hostname patterns, and it has to cover both.** The app previews are `pr-*-forever-pto-development` and the docs previews are `pr-*-forever-pto-docs-development`, which the first pattern does not match: it ends in `-forever-pto-development` and the docs one ends in `-docs-development`. Both are destinations on the same Access application, so both inherit its policies and neither needs a service token of its own. A docs preview left outside Access is not a small leak: [`apps/docs/public/robots.txt`](https://github.com/fbuireu/forever-pto/blob/main/apps/docs/public/robots.txt) says `Allow: /` and points at the **production** sitemap, so every preview would invite crawlers to index a full copy of the docs site competing with `docs.forever-pto.com`.
- **`robots.txt` cannot be the mechanism here, which is why Access is.** The `build` job produces one artifact, `docs-dist`, and both `preview` and `deploy` download that same artifact; the docs build reads no environment variable at all. So there is no build-time switch that could emit `Disallow: /` for a preview and `Allow: /` for production without building twice, and `apps/docs` ships static assets with no Worker in front of them, so there is nowhere to vary a header per environment either. Removing the docs destination from the Access application therefore has no fallback.

## Local development

- `pnpm preview`: OpenNext build + local `workerd` preview, the closest thing to production.
- `next dev` still works because `next.config.ts` calls `initOpenNextCloudflareForDev()`, which materializes the wrangler bindings (R2, the rate limiter, vars) inside the dev server.
- Local Worker secrets live in `.dev.vars` (gitignored); see [secrets](/infra/secrets/).
- `pnpm cf:typegen` regenerates `cloudflare-env.d.ts` from the wrangler config (generated on demand, not committed).

Heads-up for Windows contributors: `cf:build` is known to fail locally on Windows; CI builds on Ubuntu, and `next dev` is unaffected.
