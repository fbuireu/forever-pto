The homepage sections (`Hero`, `Features`, `Comparison`, `HowItWorks`, `Pricing`, `Stats`, `Testimonials` under `apps/web/src/ui/modules/pages/homepage/sections/`) share **class-string constants** rather than components, the planner call to action (`QuickStartTrigger`) aside. This file is pure data (a type, the `dayCell` class map, the `brutCard` class string, a fixture array, the showcase plan and its ratio), which is why this page can import it and render the real styles live.

## brutCard

The marketing card frame. Every homepage section that draws a card uses this exact string:

The current value, imported from the app (never copied into the docs):

Note the **deliberate 4px border**: core primitives like [Button](/design-system/components/button/) and Card use a 3px frame, but homepage cards go one heavier so marketing sections read louder than app chrome. If you see a 4px border anywhere else, it is a bug; here it is the point.

## dayCell

`dayCell` is a `Record<DayType, string>` mapping each calendar day type to its cell classes. `Hero` and `Features` use it together with `CAL_ENTRIES`, a 28-entry fake month exported from the same file, to render the illustrative mini-calendars:

<DayCellsDemo client:visible />

<VariantsTable rows={DAY_TYPE_ROWS} />

The visual language matches the real planner: holidays get the yellow gradient with a full-strength frame, PTO days the brand teal, weekends recede onto the soft panel surface, and plain work days sit on the card background with a faint 15%-opacity border.

## SHOWCASE_PLAN

Every figure the homepage quotes about a plan comes from one constant, `SHOWCASE_PLAN`, a plan the engine produced: {SHOWCASE_PLAN.ptoDays} PTO Days turned into {SHOWCASE_PLAN.effectiveDays} Effective Days, around {SHOWCASE_PLAN.holidays} Holidays (the values above are read from the app, not copied). `SHOWCASE_RATIO` beside it is the division, never a typed number. `Hero` shows the plan in its mock-up, `Stats` quotes the ratio and the Effective Days, and `Comparison` quotes the ratio in its copy; each formats the ratio with the locale's number format, and the translations take it as a `{ratio}` placeholder.

It exists because the same ratio used to be typed three times, and read 3.3, 3.36 and 3.4 on one page. It names no year on purpose, so the homepage does not go stale when the calendar turns. When the engine changes what it produces, re-run the plan and change this constant, and every section follows.

## Usage

```tsx
// From a sibling homepage section (src/ui/modules/pages/homepage/sections/)
import { brutCard, CAL_ENTRIES, dayCell } from './shared';

<article className={`${brutCard} p-6`}>…</article>

{CAL_ENTRIES.map(({ id, type }) => (
  <div key={id} className={dayCell[type]} />
))}
```

## Conventions

- These constants are homepage-scoped. App surfaces (planner, sidebar) style day cells through `apps/web/src/ui/modules/pages/planner/calendar/utils/helpers.ts` instead, and do not import `shared.ts` outside `apps/web/src/ui/modules/pages/homepage/`.
- Extend the pattern by adding to `shared.ts`, not by copying class strings into a section: the constants exist precisely so the sections cannot drift apart.
