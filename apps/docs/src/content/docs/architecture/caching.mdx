Caching happens at two levels: an R2-backed incremental cache at the OpenNext/Workers level, and plain `Cache-Control` headers for the agent-facing markdown surface. Next's Cache Components are deliberately not a third.

## Cache Components are off

`next.config.ts` sets `cacheComponents: false`, and no file carries a `'use cache'` directive. The flag was on, with three `cacheLife('days')` sites (`getCurrentYear`, `getPublicEnv`, the `Testimonials` section), until it was found to hang requests on the Workers runtime: production logged Next's *cannot guarantee that Cache Components will run as expected due to the current runtime's implementation of `setTimeout()`* warning followed by the runtime cancelling the request as hung, and the same thing reproduced locally on workerd. Turning the flag off made every route answer in under a second with no errors. The evidence, the alternative that did not build and the cost are in [ADR 0015](https://github.com/fbuireu/forever-pto/blob/main/adr/0015-cache-components-stay-off-on-the-workers-runtime.md).

What that means for rendering: the `[locale]` pages are plain SSG through `generateStaticParams`, built once per deploy, and the three values that used to be cached fragments are computed at build. `sitemap.ts` is the one route that opts into `export const dynamic = "force-dynamic"`, so a preview Worker names its own host. Re-enabling the flag is a decision that has to come with the ADR's reproduction run green on workerd.

## OpenNext incremental cache on R2

The app deploys to Cloudflare Workers via OpenNext. `open-next.config.ts` selects the R2 incremental cache:

```ts
import { defineCloudflareConfig } from '@opennextjs/cloudflare';
import r2IncrementalCache from '@opennextjs/cloudflare/overrides/incremental-cache/r2-incremental-cache';

export default defineCloudflareConfig({
  incrementalCache: r2IncrementalCache,
});
```

At runtime this is backed by the R2 bucket bound as `NEXT_INC_CACHE_R2_BUCKET` in `wrangler.toml`, with separate buckets per environment (see [environments](/infra/environments/)). Everything Next.js would put in its incremental cache (prerendered pages, fetch cache) is persisted there, so cache entries survive Worker isolate recycling and are shared across the fleet.

## HTTP-level caches

- **Markdown renditions**: the [proxy](/architecture/proxy/) sets a one-hour public `Cache-Control` header on `/api/markdown` responses and on the `Accept: text/markdown` rewrites that target it.

## What is deliberately not cached

API routes that carry user state opt out explicitly: `apps/web/src/app/api/check-session/route.ts` wraps every response in `noStore()` from `apps/web/src/infrastructure/api/response.ts`, since premium-session payloads must never be shared between users.
