Telemetry converges on **Better Stack** (Logtail), fed from several surfaces: the Cloudflare platform, the server runtime, the browser, plus Google Analytics for product metrics.

## Cloudflare Workers observability

`wrangler.toml` enables platform observability for the worker in every environment: invocation logs and traces, both head-sampled (see the `[observability]` blocks in the file for the current rates). This is the "free" layer, covering request outcomes, CPU time and exceptions, queryable in the Cloudflare dashboard without any code.

## The tail worker

`apps/web/workers/tail/index.ts` is a **separate Worker** (`forever-pto-tail`, own `wrangler.toml`, deployed by the `deploy-tail` job of `ci.yml`) attached to the app via `[[tail_consumers]]` in each environment. Its `tail()` handler receives batches of tail events from the main Worker, flattens each event's `logs` and `exceptions` into structured entries (timestamp, level, message, plus script name, outcome, URL, method and response status), and POSTs them to `BETTER_STACK_INGESTING_URL` with the source token as a bearer. This is what gets `console.*` output and uncaught exceptions from production into Better Stack with zero latency cost on the request path.

It checks what comes back. The handler used to await the POST and discard the response, so a 401 from a rotated token, or any 5xx, stopped logging with nothing to show for it. A non-`ok` status and a thrown `fetch` are both reported through the Worker's own `console.error`, which its `wrangler.toml` retains by declaring `[observability]` with invocation logs and no sampling.

## Request traces

Cloudflare's own traces stay in the Cloudflare dashboard: the platform exports them nowhere and the tail Worker never receives spans. What Better Stack shows in the SPANS stream is produced by the app. `apps/web/worker.ts` is the Worker entrypoint `wrangler.toml` names: it imports the handler OpenNext writes and exports it through `instrument` from `@microlabs/otel-cf-workers`, which opens a root span per request and a child span per outbound `fetch` (Stripe, Turso, the R2 cache) and ships them over OTLP to the `/v1/traces` path of the same host and token the logs use. `apps/web/src/infrastructure/clients/logging/better-stack/tracing.ts` builds that configuration from the two Worker bindings the tail Worker also reads; with either unbound it exports into a sink that acknowledges and discards, so a hand-run deploy traces into nothing rather than into a broken address. Sampling is head-based at `TRACE_SAMPLING_RATIO`, the same fraction Cloudflare's traces get, and a caller cannot raise it through a `traceparent` header.

Inside a request, every use case is a named child span: each export under `apps/web/src/application/use-cases` ends in `Effect.withSpan`, and `tracer.ts` bridges Effect spans onto the OpenTelemetry tracer the wrapper registered, so a trace reads `createPayment` → `fetch api.stripe.com` → `fetch` to Turso rather than a request followed by anonymous calls. The decision and the two alternatives it beat are in [ADR 0016](https://github.com/fbuireu/forever-pto/blob/main/adr/0016-traces-reach-betterstack-by-wrapping-the-opennext-entrypoint.md).

## Server-side logging

- `apps/web/src/infrastructure/clients/logging/better-stack/client.ts` holds `getBetterStackInstance()`, the client plain code uses directly ([country detection](/how-it-works/country-detection/), stores, services). Under it, one `@logtail/edge` `Logtail` transport per request, keyed on the Cloudflare execution context and configured with `NEXT_PUBLIC_BETTER_STACK_SOURCE_TOKEN` / `NEXT_PUBLIC_BETTER_STACK_INGESTING_URL`: a request's lines batch together and flush inside its own `waitUntil`. It used to be one module-level instance, and on workerd a batch timer armed by one request delivering another request's lines is an I/O violation the runtime cancels the request for. Off a request there is no `waitUntil`, so the transport is throwaway and flushes at once.
- Every entry carries the active span's `traceId` and `spanId`, read off the OpenTelemetry context by `correlation.ts`, so a log line and the span it failed on answer one query.
- `apps/web/src/infrastructure/clients/logging/better-stack/service.ts` holds `LoggerService`, the Effect wrapper used inside use-cases; it is part of `ApplicationLayer`.

A privacy convention runs through all call sites: log the email **domain**, ids and flags, never full addresses or payloads.

## Browser analytics: typed `track()`

`apps/web/src/infrastructure/clients/logging/better-stack/tracking.ts` exposes `track({ event, properties })` and `identifyUser({ email, plan })` over `window.betterstack`. Event names are a closed union (`TrackEventName`): `payment_started`, `payment_completed`, `payment_failed`, `promo_code_applied`, `premium_activated`, `upgrade_modal_opened`, `feature_unlocked`, `planner_generated`, `contact_form_submitted`, so a typo or ad-hoc event is a compile error. Both functions no-op when the script is absent (SSR, consent denied).

The script itself is injected by `apps/web/src/ui/modules/tracking/BetterStackTracking.tsx`, mounted in the root layout but rendering nothing until the analytics [consent category](/how-it-works/cookie-consent/) is accepted and `NEXT_PUBLIC_BETTER_STACK_TRACKING_TOKEN` is set. Once consented, premium users are identified with `identifyUser({ email, plan })`, where `plan` is `'premium' | 'free'`.

That snippet is Better Stack's real user monitoring tag, not only an event pipe: once loaded it also captures browser errors, session replays, web vitals and console logs, and which of those run, at what sampling, is configured remotely in the Better Stack application, so a change there needs no deploy. Two things are set from code because the tag cannot know them. The **release** is the app version from `apps/web/package.json`, passed through `betterstack('config', { release })`, so an error is grouped under the version that produced it. The **environment** is derived from the hostname by `trackingEnvironment(hostname)`: `localhost` and any `.workers.dev` host, which is where a pull-request preview lives, report `development`, everything else `production`. It used to read `NODE_ENV`, which every deployed build sets to `production`, so preview traffic was filed with the live site's.

## Google Analytics

`apps/web/src/ui/modules/tracking/Analytics.tsx` loads gtag (`NEXT_PUBLIC_GOOGLE_ANALYTICS_ID`) with **Consent Mode defaults of denied** for all storage types; the consent component upgrades `analytics_storage` only after opt-in. GA covers acquisition/product analytics; Better Stack events cover behavioral telemetry the team actually alerts on.

## Where to look when debugging

- Request failed in production → Better Stack (tail worker entries carry URL, method, status, outcome).
- Effect use-case errors → Better Stack via `LoggerService` with structured context.
- Client-side behavior funnels → Better Stack events; page analytics → GA.
