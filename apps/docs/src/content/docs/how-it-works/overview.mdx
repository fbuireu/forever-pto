The planner is a browser application with a thin server in front of it. This page is the map: which piece runs where, in what order, and what crosses each boundary. Each step links to the page that covers it in depth.

## The runtimes

There are three places code runs, and they never share memory:

```mermaid
---
config:
  look: handDrawn
  layout: dagre
---
flowchart TB
  subgraph cf [Edge: Cloudflare Worker]
    P["Proxy +<br/>prerendered pages"]
    R["Route handlers,<br/>Server Actions"]
  end
  subgraph browser [Browser]
    UI["Planner screen"]
    ST["Stores +<br/>Holiday lookup"]
    ENG["Planning engine<br/>(Web Worker)"]
  end
  subgraph ext [External services]
    PAY["Stripe, Turso,<br/>Resend"]
    GEO["Cloudflare trace,<br/>ipify, ipinfo"]
  end
  P -->|"HTML + cookies"| UI
  UI <--> ST
  ST <-->|"ISO strings"| ENG
  UI -->|"Donation, session,<br/>contact"| R
  R <--> PAY
  P -.->|"no user-country<br/>cookie"| GEO
```

- **The Worker** serves prerendered HTML, runs the [proxy](/architecture/proxy/) on every page request and hosts the API routes. It never sees a plan.
- **The main thread** holds the stores, renders the planner and fetches Holidays. The Holiday data ships in the client bundle, so "fetch" here is a library call, not a network request.
- **The Web Worker** runs the engine. It receives plain data and returns plain data; it has no access to the DOM or the stores.

## The first request

```mermaid
---

  look: handDrawn
  layout: dagre
  sequence:
    wrap: false
    width: 90
    actorMargin: 10
---
sequenceDiagram
  autonumber
  participant B as Browser
  participant P as Proxy (edge)
  participant CF as Cloudflare trace
  participant IP as ipify, ipinfo
  B->>P: GET /planner
  Note right of P: Markdown? payment guard?
  Note right of P: next-intl resolves the locale
  alt the request carries user-country
    Note right of P: re-set it, detect nothing
  else no user-country cookie
    Note right of P: cf-ipcountry, final if present
    opt no cf-ipcountry (local development)
      P->>CF: GET /cdn-cgi/trace
      CF-->>P: loc= line, or nothing
      opt still no country
        P->>IP: egress IP, then its country
        IP-->>P: country code, or nothing
      end
    end
  end
  P-->>B: HTML, user-country if known,<br/>NEXT_LOCALE if written
  Note over B,P: stores rehydrate<br/>from localStorage,<br/>StoresInitializer<br/>seeds the Country
```

1. The [proxy](/architecture/proxy/) runs its chain: Markdown negotiation for agents, the payment-confirmation guard, locale resolution and, last, [country detection](/how-it-works/country-detection/). The result is a prerendered page with the `user-country` cookie whenever a Country is known, and with `NEXT_LOCALE` only when the navigation changed the locale.
2. The browser rehydrates the persisted [stores](/how-it-works/state-stores/) from `localStorage`: `filters`, `holidays` and `premium` carry data, `location` persists an empty object and `ui` nothing. Every persisted store revives its dates from ISO strings and wipes its own key when it cannot parse the blob ([rehydration](/how-it-works/state-stores/#rehydration-on-every-page-load)).
3. `StoresInitializer` (`apps/web/src/ui/modules/stores/StoresInitializer.tsx`) reads the `user-country` cookie and seeds the filters store's Country, only when the user has never chosen one.

## The planning loop

Everything after that is one loop, closed inside the browser: when the visitor changes a Country, the budget or any other planner input, the store changes and the planner asks a Web Worker for the new plan, so the main thread never freezes while it is computed. `CalendarList` (`apps/web/src/ui/modules/pages/planner/CalendarList.tsx`) owns it: one effect refetches Holidays when the Country, Region, year, Carry-over Months or locale change, and another triggers a calculation when any planning input changes or the store bumps its `planRevision`.

```mermaid
---
config:
  look: handDrawn
  layout: dagre
  sequence:
    wrap: false
    width: 90
    actorMargin: 10
---
sequenceDiagram
  autonumber
  participant FS as filters store
  participant CL as CalendarList
  participant HS as holidays store
  participant WK as Web Worker
  FS-->>CL: a planner input changed
  CL->>HS: fetchHolidays, when the<br/>Country, Region, year,<br/>Carry-over Months<br/>or locale changed
  HS-->>CL: HolidayDTO[] merged<br/>with Custom Holidays
  CL->>WK: triggerCalculation,<br/>one reused worker,<br/>the latest request wins
  Note over CL,WK: CALCULATE_SUGGESTIONS with a requestId,<br/>every Date as an ISO string
  Note left of WK: runPlanningPipeline:<br/>Workdays, Bridges,<br/>Strategy, Alternatives,<br/>Metrics
  WK-->>CL: CALCULATE_SUGGESTIONS_RESULT<br/>or WORKER_ERROR
  CL->>HS: setCalculating(false), then<br/>setCalculationResult<br/>on a result
  HS-->>FS: calendar, budget readout<br/>and Summary repaint
```

- **Holidays** come from the `date-holidays` package, looked up for the chosen year and the next, once for the Country and once for the Region, then filtered to non-working types and shaped into `HolidayDTO`. The [holidays engine](/how-it-works/holidays-engine/) page has the rules; [data sources](/how-it-works/data-sources/) has the provenance.
- **The worker** is spawned on the first calculation and reused for every one after it. A request made while one is in flight is held, a later one replaces it, and only the latest reply reaches the store. [Planner recalculation](/how-it-works/calculation-worker/) follows one change from the click to the repainted plan, including what the visitor sees meanwhile and when it fails.
- **The engine** is `runPlanningPipeline` in `apps/web/src/domain/calendar/pipeline.ts`: clear the caches, expand the Planning Window into months, fold Manual Days in as pseudo-Holidays, measure the Remaining Budget, find Workdays and Bridges, select under the Strategy, build Alternatives, measure everything. The [planning algorithm](/how-it-works/planning-algorithm/) page walks each stage.
- **The result** lands in the holidays store, and every planner component reads it back from there: the calendar paints Suggested, Manual and Alternative days, the panel shows the budget and the Alternative switcher, the Summary renders the Metrics. The [planner UI](/how-it-works/planner-ui/) page maps the screen.

## What each boundary carries

| Boundary | Carries | Never carries |
| --- | --- | --- |
| Edge → browser | HTML, `NEXT_LOCALE`, `user-country` | Any planning input or output |
| Store → `localStorage` | Filters, Holidays, the Suggestion, Alternatives, Manual and Removed Days, all dates as ISO strings, [obfuscated](/how-it-works/data-protection/) with a build-time key | The year (it resets on every visit), loading flags |
| Main thread → worker | `CalculateSuggestionsRequest`: window, budget, serialised Holidays, Strategy, locale, Manual and Removed Days as ISO strings | `Date` objects, store references |
| Worker → main thread | `WorkerResponse`: a measured Suggestion and its Alternatives, or a stringified error, echoing the `requestId` | Anything for a stale `requestId` (the hook drops it) |
| Browser → server | A Donation intent and a contact message through Server Actions, a session check and an activation through `/api/check-session` | The plan |

The one-way arrows are the design. A plan is never uploaded, so the server cannot lose it, leak it or need an account to attach it to; the cost is that a plan lives in one browser unless the user exports it, which is what the [ICS and PDF exports](/how-it-works/exports/) are for.

**Offline, the loop keeps going as far as its code has arrived.** There is no service worker. Once the page, the Holiday lookup and the worker chunk have loaded, a change still re-plans with no network, because nothing in the loop calls one. A chunk that has not loaded yet fails instead, as [planner recalculation](/how-it-works/calculation-worker/#when-it-fails-or-never-loads) and the [holidays engine](/how-it-works/holidays-engine/#failure) describe, and the Donation, the contact form and the session check fail the way their pages say, each reporting its own error rather than a blank page.

## Server-side flows

The API routes exist for the parts a browser cannot do alone, and each has its own page:

| Flow | Entry | Page |
| --- | --- | --- |
| Donation and Premium activation | The `createPaymentAction` Server Action (`POST /api/payment` for outside callers), `POST /api/check-session` after an in-page card confirmation, `GET /api/payment/activate` after an issuer redirect, `POST /api/webhooks/stripe` | [Premium](/how-it-works/premium/) |
| Premium session | `GET`/`POST /api/check-session` | [Premium](/how-it-works/premium/#the-session-premium-token-cookie) |
| Contact form | The `sendContactEmailAction` Server Action (`POST /api/contact` for outside callers) | [Emails](/how-it-works/emails/) |
| Agent-facing renditions | `Accept: text/markdown`, `/.well-known/*` | [Markdown API](/how-it-works/markdown-api/), [WebMCP](/how-it-works/webmcp/) |
| Abuse control on the payment routes | The `PAYMENT_RATE_LIMITER` binding | [Rate limiting](/how-it-works/rate-limiting/) |
| Telemetry: invocation logs, spans, the app's own log lines, the browser tag | The platform export named in `wrangler.toml`; nothing in the app opens a connection | [Observability](/how-it-works/observability/) |
| Signed session, constant-time secret check, webhook signature, obfuscated storage | Where the app applies a primitive, and where it deliberately does not | [Data protection](/how-it-works/data-protection/) |

All of them are Effect programs provided with one `ApplicationLayer`; see [Effect layers](/architecture/effect-layers/).
