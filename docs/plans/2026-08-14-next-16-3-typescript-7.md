# Next 16.3 + TypeScript 7 — what landed, what is left

Date: 2026-08-14

The dependency bump moved TypeScript from 6 to 7 and Next from 16.2 to 16.3. Those two are one decision,
not two, and the ordering is not optional — this plan records why, what the bump already unlocked, and what
is still on the table.

## Why the two versions move together

TypeScript 7 is the Go compiler. It ships no `lib/typescript.js`, so the JavaScript compiler API is gone.
Next's type-checking step loaded exactly that file, which is why the root guide capped this repo at
TypeScript 6 until now. Next 16.3 replaces that path: `next build` shells out to the project-local `tsc`
binary instead, and the switch is the **default** — `experimental.useTypeScriptCli` exists only as the
opt-out back to the compiler API, and setting it `false` while TypeScript is 7 fails the build outright.

So: Next 16.3 first, TypeScript 7 second. Downgrading Next below 16.3 without downgrading TypeScript first
kills `pnpm build` before it type-checks anything.

## Status: done and verified

| Change | Verification |
| --- | --- |
| `typescript` 6.0.3 → 7.0.2 | `pnpm lint:ts:typecheck` exits 0 across the whole project |
| `next` 16.2.12 → 16.3.0 | `pnpm build` exits 0 |
| `partialPrefetching: true` in `next.config.ts` | build reports Partial Prerender on the `[locale]` routes |
| `@typescript/typescript6` added, `docs/docs-consistency.test.ts` re-pointed at it | 35/35 tests pass |
| `next-env.d.ts` picks up `.next/types/root-params.d.ts` | regenerated by the 16.3 build |

The 7 migration cost this repo almost nothing, because the options 7 removes or re-defaults were already
right in `tsconfig.json`: `baseUrl` had been dropped ahead of time, `strict` and `esModuleInterop` were
already on, `types` was already an explicit `["node"]` instead of the implicit everything, and
`target`/`module` were already `ESNext`. No source file under `src/` needed an edit.

### The one thing that did break

`docs/docs-consistency.test.ts` parses source files with the compiler API to enforce the no-comments rule,
so it was the only file in the tree that depended on `lib/typescript.js`. It now imports
`@typescript/typescript6`, Microsoft's compatibility package pinning the 6.x API. That is a parser for one
test, not a second toolchain — delete it when 7.1 ships the replacement API.

### Two behaviours that changed under you

- **Build output lost its Next-specific framing.** `tsc` prints its own diagnostics now, so the code frames
  and the rewritten messages for pages, layouts and route handlers are gone.
- **The production build type-checks more than it used to.** The CLI checks the entire project the
  `tsconfig` selects — tests and `.next/dev/types` included — so a type error in a `*.test.ts` now fails
  `pnpm build`, not only `pnpm lint:ts:typecheck`. `next build --debug-build-paths` cannot narrow that set
  and warns if combined with the CLI checker.
- **The editor plugin stops loading if you point VS Code at the workspace TypeScript.** The
  `{ "name": "next" }` entry in `tsconfig.json` is a `tsserver` plugin, and 7's language server is Go with
  no JavaScript plugin host. Leave VS Code on its bundled TypeScript to keep the `'use client'` and
  segment-config checks.

## Open: the Cloudflare half is unverified

`pnpm build` passing proves Next is happy. It proves nothing about the deployed Worker, and that is where
the remaining risk sits.

`@opennextjs/cloudflare` 1.20.2 is the latest published version and it predates Next 16.3 by two weeks. The
adapter documents support for "all minor and patch versions of Next.js 16", but `cacheComponents` and
`partialPrefetching` on Workers have not been exercised here. Upstream has one open regression against
16.3 — `patchTurbopackRuntime` no longer matches, leaving Wasm modules with a Node-only loader — which does
**not** bite this repo: the build emits no `.wasm` at all. Its failure mode is still worth internalising,
because it is the shape every adapter break takes here: build, dry-run and unit suite all pass, and nothing
fails until a request hits the deployed Worker.

**Next step, and it is a gate, not a nicety:** open a PR so CI deploys a preview worker and run
`pnpm test:e2e` against it. `pnpm preview` locally is the other half, but `cf:build` is known broken on
Windows, so the preview deploy is the practical route.

## Candidates, in the order they are worth doing

### 1. Stop tracking `next-env.d.ts`

Next's documentation now says the file is an implementation detail, that it belongs in `.gitignore`, and
that projects already tracking it should remove it from Git. That is the documented fix for the flapping
described in the root guide — the file's contents differ depending on whether a dev run or a production
build touched it last, and the guide currently asks people to leave the flip alone. Untracking it deletes
the gotcha instead of managing it. Cheap, contained, removes a paragraph of maintenance.

### 2. Rename the middleware to the proxy convention

Next 16 deprecated the `middleware` file convention and the `middleware` named export in favour of `proxy`.
The build already labels it `ƒ Proxy (Middleware)`. Migration is a rename of `src/middleware.ts` and
`src/middleware.test.ts` to the proxy names, the exported function with them, plus the folder tree in the
root guide.

Two things make this its own PR rather than a drive-by. `proxy` runs on the Node runtime and that is not
configurable — no edge runtime — so the deployed behaviour has to be re-verified on Workers. And the file
carries the locale cookie, the country cookie and the markdown rewrite, so a silent break shows up as
wrong-language pages rather than an error. `next-intl`'s `createMiddleware` is unaffected: `proxy` is a
Next file convention, not a `next-intl` API change.

### 3. `next/root-params`

16.3 lets any Server Component read a root-level dynamic param without prop-drilling, and it works inside
`use cache` scopes. This app's entire tree sits under `[locale]`, so the locale is exactly the param the
feature was built for. The build already generates `.next/types/root-params.d.ts`. Worth a focused pass to
see how much threading it removes before committing to it.

### 4. `instant()` Playwright helper

16.3 ships `@next/playwright` with an `instant()` helper that asserts what is visible during a navigation
before the network resolves. With `partialPrefetching` now on, this is the regression test that catches a
future refactor quietly de-opting a route back to a blocking navigation. Pairs directly with the flag that
was just enabled, so it is the natural companion to it.

### 5. Deliberately not now

- `experimental.turbopackRustReactCompiler` and `reactCompiler` — experimental, and the repo does not run
  the React Compiler at all today, so this is two changes wearing one flag.
- `experimental.useOffline` — experimental, and offline behaviour is not a stated product requirement.
- `typedRoutes` and `experimental.typedEnv` — real wins, but both add generated type surface, and
  `environment.d.ts` is hand-declared on purpose. Revisit once the deploy is green.
- `wrangler` 4.123.0 — `pnpm-workspace.yaml` sets `minimumReleaseAge: 4320`, so anything published in the
  last three days is unresolvable. 4.120.1 is what the bump could reach, and the `--message` finding in the
  root guide was made against 4.115 and has not been re-verified since.

## Bumps that carried a real risk and did not bite

- **`motion` 12 → 13** is a major. Its only React-side breaking change is dropping `@emotion/is-prop-valid`
  as an optional dependency, which affects Styled Components and Emotion users. This repo is Tailwind, all
  49 imports come from `motion/react`, and nothing references `framer-motion` or `is-prop-valid`.
- **`@base-ui/react` 1.6 → 1.7**, `stripe` 22.4 → 22.5, `resend`, `sonner`, `react-hook-form`,
  `next-intl` 4.13.4 → 4.13.6 — minors, all covered by the clean type-check and the build.

## Not covered by any executable rule

`docs/docs-consistency.test.ts` asserts the `tsconfig` settings `next build` would otherwise fill in, but
nothing asserts the coupling this plan is about: that `next` stays at or above 16.3 while `typescript` is
7, or that `@typescript/typescript6` stays present for the docs test's own parser. Both are one-line
version reads away from being checkable, and both are the kind of thing a future bump breaks silently.
