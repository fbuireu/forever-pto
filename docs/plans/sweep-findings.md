### Manual Days are persisted with no Planning-Window key, so they survive a year change invisibly and silently consume the PTO budget

`src/application/stores/holidays.ts:533` · 

**Fails when:** User is on 2026 with a 22-day budget, switches the year selector to 2027, and manually assigns 3 days in July 2027. They reload the page. `filters` does not persist `year`, so the app comes back on 2026, but the holidays store revives the three July-2027 dates. CalendarList only renders 2026 + carry-over months, so those three cells never appear and cannot be un-toggled. useCalculationsWorker.ts:62 / worker.ts:51 then plan 2026 with 19 instead of 22 PTO days; PlannerPanel Status shows "manual: 3" and "remaining: 0" while only 19 days are actually placed on the visible calendar. generateMetrics folds the 2027 dates into the July bucket of the 2026 monthlyDist/quarterDist charts, and the ICS export emits them. The only recovery is the "reset manual changes" button, which also throws away any legitimate in-window Manual Days.

**Why it is real:** Every load-bearing claim checks out.

1. `partialize` (holidays.ts:533-534) writes `manuallySelectedDays`/`removedSuggestedDays` as bare ISO strings with no year/country key; `onRehydrateStorage` (580-586) revives them verbatim.
2. I grepped every write to `manuallySelectedDays` in src/: the only clears are `setCurrentAlternativeSelection` (316), `resetManualSelection` (443-468), `resetToDefaults` (328), `trimManualDays` (470, ptoDays-driven only) and `toggleDaySelection`. Nothing is keyed on `year`, `country` or `carryOverMonths`. `setYear` (filters.ts:54) only sets the year, and `setCalculationResult` (295-303) explicitly clears `removedSuggestedDays` but deliberately keeps `manuallySelectedDays`.
3. `filters` partialize (63-70) genuinely omits `year`, and there is no startup effect that re-forces it — I grepped `getFullYear()` across src/ and the only writer is the initial state (filters.ts:40). So a reload really does snap the year back to the current one while the holidays blob revives the other year's Manual Days.
4. Reachability is high, not exotic: `Years.tsx:32` offers `currentYear-5 .. currentYear+4`, and planning *next* year is the primary use case — so "pick manual days for 2027, reload" is the common path, not just an explicit year switch.
5. Budget impact confirmed end-to-end: `useCalculationsWorker.ts:62` computes `budgetForAutoSuggest = ptoDays - manuallySelectedDays.length`, and with `lastCalculatedPtoDaysRef.current === null` on a fresh mount `ptoDaysChanged` is false, so `autoSuggestCount = Math.min(budgetForAutoSuggest, activeSuggestedDays)`; worker.ts:51 then uses `Math.max(0, autoSuggestCount ?? ptoDays - manualDays.length)`. Either branch loses the days.
6. No consumer filters by window: `CalendarList.tsx:61-65`, `PlannerPanel.tsx:270-273` (Status) and `holidays.ts:477-482` all use the raw `.length`; `resolveSelectedDays` (selection.ts:17) blindly concatenates; `generateMetrics` then buckets by `getMonth()` (`getMonthlyDist`) so an out-of-year date lands in the wrong chart, and `days[0].getFullYear()` (generateMetrics.ts:70,77) can even resolve to the wrong year entirely when a stale Manual Day sorts first.
7. `CalendarList.tsx:109` only renders `getTotalMonths({carryOverMonths, year})`, so the offending cells are genuinely unclickable — the only escape is the `resetManual` button (PlannerPanel.tsx:324), which is at least visible since `hasManualChanges` is true.

The CONTEXT.md rule the candidate cites is accurate: "Manual Days survive recalculation" (CONTEXT.md:73) is about recalculation, and "Planning Window" (CONTEXT.md:22) is defined as year + Carry-over Months. Nothing in the glossary says Manual Days outlive their Window.

**Fix:** Scope the Manual/Removed day sets to the Planning Window that produced them. Minimal fix: persist the `year` + `carryOverMonths` they were created under (e.g. a `manualDaysWindow: {year, carryOverMonths}` field in partialize) and add a `pruneDaysOutsideWindow({year, carryOverMonths})` action to the holidays store that filters both arrays to `[startOfYear(year), endOfMonth(addMonths(endOfYear(year), carryOverMonths))]`. Call it from `onRehydrateStorage` and from the same effect that refetches holidays on window change (CalendarList.tsx:75-78), before the calculation effect at line 80 fires, so the freed budget is picked up by the very next run. If losing the days on a year toggle is unacceptable product-wise, key them per year instead (`manuallySelectedDays: Record<number, Date[]>`) and have every consumer read `manuallySelectedDays[year]`. Either way `removedSuggestedDays` needs the same treatment, and holidays.test.ts should gain a case asserting that out-of-window manual days do not reduce the budget.

### Effective days are summed across bridges whose absorbed free days overlap, double-counting the same weekend — FIXED

`src/domain/calendar/metrics/utils/helpers.ts:50` · 

**Fails when:** Verified by running the shipped engine: generateSuggestions({ year: 2025, ptoDays: 2, months: [Jan 2025], holidays: [Jan 1], strategy: OPTIMIZED }) returns days [Fri Jan 03, Mon Jan 06] with bridges [Fri Jan 03 - Sun Jan 05, effectiveDays 3] and [Sat Jan 04 - Mon Jan 06, effectiveDays 3]. generateMetrics then reports totalEffectiveDays 6, averageEfficiency 3.0, bonusDays 4 — while the actual continuous stretch is Jan 3 to Jan 6 = 4 days, which `calculateLongestVacation` (same file, line 177) correctly returns as 4. Sat+Sun are counted twice. Every headline figure on the Summary panel is 50% high for this plan.

**Why it is real:** Could not refute; reproduced with the real engine. `analyzePotentialBridge` (src/domain/calendar/utils/helpers.ts:43-66) expands each bridge outward through adjacent free days and stores that whole span as `effectiveDays`, so two bridges on either side of the same weekend both include it. Neither selector rejects that: `canSelectBridge` (suggestions/utils/selectors.ts:16) and the GROUPED/OPTIMIZED loop (selectors.ts:160) only test for shared `ptoDays`, and `deduplicateBridges` (utils/helpers.ts:83-99) keys on `ptoDays` alone, so no guard elsewhere prevents it. `getTotalEffectiveDays` then does a flat `reduce((sum, b) => sum + b.effectiveDays)` (line 50); the same flat accumulation appears at selectors.ts:111 and selectors.ts:168. The number is user-visible in three places: Summary.tsx:115/267/336, PlannerPanel.tsx:92-94, ManagementBar.tsx:90-91. Note this is NOT the escalated Summary.tsx baseline question — that one is about which denominator to compare against; this is the numerator itself being wrong. The secondary claim in the finding (a manual day adjacent to a bridge counted as a standalone +1) is technically true of line 51 but usually harmless, since a manual day adjacent to an already-expanded bridge normally does add exactly one day; the overlap half is the real defect.

**Fix:** Replace the flat reduce in `getTotalEffectiveDays` with a union: walk each valid bridge's [startDate, endDate] with `eachDayOfInterval`, add each date key to a Set, then add any selected day not already in that Set; return the Set size. Apply the same union to the `totalEffectiveDays` returned by `selectOptimalDaysFromBridges` (selectors.ts:111) and `selectBridgesForStrategy` (selectors.ts:168) so the selectors' own ranking is not skewed by the same inflation. Optionally also make range overlap a conflict in `canSelectBridge` — but that changes which plan is produced, so treat it as a separate decision. Add a regression test with two bridges that share a weekend.

### autoSuggestCount cap is re-derived from the already-capped result, so the auto-suggestion count ratchets down and can lock at zero

`src/ui/hooks/useCalculationsWorker.ts:72` · 

**Fails when:** ptoDays = 3, three days suggested. User removes all three to hand-pick instead (no recalc fires). User clicks one day manually - allowed, since toggleDaySelection computes remaining = 3 - (3-3) - 0 = 3. manuallySelectedDays changes, triggerCalculation identity changes, CalendarList's effect re-runs. budgetForAutoSuggest = 2, activeSuggestedDays = 3 - 3 = 0, ptoDaysChanged = false, so autoSuggestCount = 0. worker.ts:53 short-circuits and returns {suggestion:{days:[]}, alternatives:[]}. setCalculationResult stores it and clears removedSuggestedDays. Every later recalc now computes activeSuggestedDays = 0 - 0 = 0 and returns the same empty plan: no suggestions, no alternatives, and currentSelection.metrics is undefined. Changing strategy, country or year does not recover it, and the 'reset manual changes' button does not either (it restores from the now-empty `suggestion`). Only changing the PTO-day count restores a plan.

**Why it is real:** The code reads exactly as claimed (useCalculationsWorker.ts:60-75, holidays.ts:302, worker.ts:51-61, CalendarList.tsx:91), and the chain is reachable: removals do not trigger a recalc (CalendarList's effect deps exclude removedSuggestedDays/currentSelection), but adding a manual day changes manuallySelectedDays -> new triggerCalculation identity -> effect re-fires, and getState() is read before setCalculationResult clears the removals. HOWEVER the finding is partly mischaracterised and over-severe. (a) The 'ratchets down' framing is the documented intent, not a bug: the comment at :67-69 states the cap deliberately 'respects how many days the user has left active'. It is also self-limiting, not compounding - once the run returns 17 days, activeSuggestedDays is 17 and stays 17; it does not shrink further without further removals. The mild variant is also visible and manually recoverable: remainingDays (CalendarList.tsx:61-65, PtoDays.tsx:49) shows the 3 unassigned days and the user can click them. (b) 'forever' is false. lastCalculatedPtoDaysRef is compared against params.ptoDays, so any change of the PTO-day count sets ptoDaysChanged=true, sends autoSuggestCount=undefined, and fully recovers. Changing strategy/country/year does not recover - that part is correct. (c) The genuinely defective part, which survives refutation, is the zero absorbing state: once activeSuggestedDays reaches 0 the worker short-circuits at worker.ts:53 and stores suggestion={days:[]}, alternatives=[], and (via deserializeSuggestion) currentSelection with metrics undefined, which then reproduces cap=0 on every later run. I confirmed the documented escape hatch does NOT work: resetManualSelection (holidays.ts:443-468) restores currentSelection from `suggestion`, which by then is itself the empty one, so the reset button leaves the state stuck. Net: real defect, but narrower and less permanent than described - medium, not high.

**Fix:** Treat a computed cap of 0 as 'no cap' rather than 'suggest nothing': `const cap = !ptoDaysChanged && activeSuggestedDays !== undefined ? Math.min(budgetForAutoSuggest, activeSuggestedDays) : undefined; const autoSuggestCount = cap && cap > 0 ? cap : undefined;`. Also skip the cap entirely when currentSelection.days.length === 0 (an empty selection carries no user intent to preserve). The finding's alternative suggestion of tracking the intended budget in a ref is a larger change and would alter the deliberate 'honour removals' behaviour documented at :67-69, so it should not be adopted without a product decision. Independently, worker.ts:53's empty response should carry a metrics object rather than leaving currentSelection.metrics undefined.

`src/infrastructure/workers/worker.ts:43` · 

**Fails when:** Suggestion places Mon 22, Tue 23, Wed 24 Dec; the user removes Wed 24 Dec and then adds a manual day, triggering a recalc. 24 Dec is sent as an excluded pseudo-holiday. analyzePotentialBridge expands the block through 24 Dec into 25 Dec, inflating that bridge's efficiency and biasing the selector toward it; calculateLongestVacation walks straight through 24 Dec, so the summary reports a longer continuous holiday and a higher averageEfficiency/totalEffectiveDays/bonusDays than the user will actually get, and getWorkingDaysPerMonth understates actual working days. **Why it is real:** Confirmed on all mechanical points. excludedPseudoHolidays are concatenated into holidaysWithManual (worker.ts:50) and that single array is handed to generateSuggestions, generateAlternatives and both generateMetrics calls (:68, :77, :91, :102). createHolidaySet (domain/calendar/utils/cache.ts:28-44) makes no distinction by variant, so the excluded date lands in the holidaySet used by analyzePotentialBridge's adjacency test and both expansion loops (domain/calendar/utils/helpers.ts:30-31, 50, 60) as well as in the freeDays sets of calculateLongestVacation and calculateLongWeekends (metrics/utils/helpers.ts:180, 217) and in holidaysOnWorkdays in getWorkingDaysPerMonth (metrics/utils/helpers.ts:164). So a day the user said they will work is counted as time off across bridge scoring and the displayed metrics. Manual days receive the same treatment and for them it is correct (they really are days off); for excluded days it is not. One correction to scope: this only applies to runs where removedSuggestedDays is non-empty, i.e. the single run described in the finding above - but that run's result is the one stored and displayed, so the wrong numbers persist on screen until the next recalculation. The finding's proposed fix is wrong on one point and I am correcting it: passing removedSuggestedDays into generateMetrics would be a no-op, because those days were excluded from getAvailableWorkdays and therefore are not in baseSuggestion.days, so resolveSelectedDays has nothing to subtract. The 'correct contract already exists' framing (citing toggleDaySelection at holidays.ts:430-432) does not transfer - toggleDaySelection operates on a stale currentSelection that still contains the removed days, which is a different situation.

**Fix:** Stop smuggling exclusions through the holidays array. Add an explicit `excludedDays: Date[]` parameter to generateSuggestions/generateAlternatives, subtract it inside getAvailableWorkdays only (domain/calendar/utils/helpers.ts:118-126, alongside the existing holidaySet check), and never add it to the array passed to createHolidaySet or to generateMetrics. Do NOT apply the finding's suggestion of passing removedSuggestedDays into generateMetrics - it is a no-op here because those days are already absent from baseSuggestion.days.

### A replayed or out-of-order payment_intent.payment_failed webhook downgrades an already-succeeded payment

`src/domain/payment/handlers/paymentFailed.ts:13` · 

**Fails when:** Card declined -> Stripe emits payment_intent.payment_failed; that delivery hits a transient DB/Turso error, the route returns 500, Stripe queues a retry. The user retries with a second card -> payment_intent.succeeded lands and the row becomes 'succeeded'. Stripe redelivers the failed event minutes later and handlePaymentFailed overwrites status back to 'requires_payment_method'. The donation is captured, but once the 30-day premium cookie expires the 'I already donated' path (activateWithEmail) fails with "Payment status is requires_payment_method" and the paying user loses recovery unless they still have the pi_ id.

**Why it is real:** Code confirmed exactly as described. handlePaymentFailed (paymentFailed.ts:13) calls updatePaymentStatus(event.paymentId, event.status) with no read-before-write, and updatePaymentStatus (repository.ts:61-68) is a bare `UPDATE payments SET status = ? ... WHERE id = ?` with no state predicate. handlePaymentSucceeded does guard (paymentSucceeded.ts:74 `if (existing.status !== 'succeeded')`), so the asymmetry is real. I looked for a guard elsewhere and found none: processWebhookEvent (src/application/use-cases/webhook.ts:56-59) dispatches payment_failed straight to the handler with no dedupe/idempotency table, and the route (src/app/api/webhooks/stripe/route.ts:33-35) returns 500 on any unhandled error, which is exactly what makes Stripe redeliver. The consequence chain is also real and is the entitlement mechanism itself: getPaymentByEmail filters `status = 'succeeded'` (repository.ts:129) and activateWithEmail rejects a non-succeeded row (activatePremium.ts:107-109), and docs/adr/0008 states the payment row *is* the entitlement. Two mitigations reduce the blast radius, which is why I lower the severity from high: (a) activateWithPayment does not consult the DB status at all — it re-checks Stripe — so a user who still holds the pi_ id can re-activate and the deferred branch (activatePremium.ts:46-59) even repairs the row back to 'succeeded'; (b) `succeeded_at` is preserved by the CASE expression, so the record is recoverable. The scenario also requires a decline-then-retry on the same PaymentIntent *plus* out-of-order/redelivered webhooks, which is possible but not routine.

**Fix:** Make the write terminal-state-safe rather than relying on delivery order. Cheapest correct fix is in the SQL so it also covers any future caller: add `AND status <> 'succeeded'` to the WHERE clause of updatePaymentStatus (repository.ts:66) — or, if updatePaymentStatus must stay generic, mirror the succeeded handler and read via getPaymentById in handlePaymentFailed, skipping the update when existing.status === 'succeeded'. Prefer the SQL guard: it is atomic, whereas the read-then-write in paymentSucceeded.ts:74 is itself racy under concurrent deliveries.

`src/infrastructure/services/payments/provider/promoCode.ts:12` · 

**Fails when:** An operator creates LAUNCH50 (50% off) with max_redemptions 100 and restrictions.minimum_amount 2000. ### Location proxy re-runs full country detection on every request, including when the user-country cookie already exists

`src/infrastructure/proxy/location.ts:11` · 

**Fails when:** A returning visitor with a valid `user-country=es` cookie navigates `/` -> `/planner`; middleware still awaits `detectCountryFromCDN()` before any HTML is emitted, even though the answer is already on the request. If that subrequest hangs, every page on the site — not just country detection — blocks for up to the 5 s timeout before responding.

**Why it is real:** Verified: `location()` (location.ts:10-17) calls `await detectCountry(request)` unconditionally, never reads `request.cookies.get(USER_COUNTRY_COOKIE)`, and middleware.ts:47 routes every matched navigation through it — so a cookie written with a one-week `maxAge` (cookie.ts:4,11) is recomputed on every single page request. There is no guard anywhere upstream: the markdown and payment-confirmation branches return before line 47, but every normal page falls through. The severity driver is not the steady-state cost (a same-colo subrequest, single-digit ms) but the availability coupling: an unconditional `await` on a non-essential subrequest with a 5 s `AbortSignal.timeout` sits in front of every HTML response, so a slow trace endpoint stalls the whole site's TTFB. Two sub-claims in the finding are wrong and should not be repeated: the 15 s worst case needs the trace to hang for its full timeout *and* `cf-ipcountry` to be absent, which on the production zone it never is (so production tops out near 5 s; the 15 s tail is preview/`wrangler dev` only); and 'the cookie is attached to a 307 the browser immediately discards' is incorrect — browsers do persist `Set-Cookie` from redirect responses, so that work is not wasted.

**Fix:** In `location()`, short-circuit when the cookie is already present, but re-set it rather than returning bare so the one-week window slides: `const existing = request.cookies.get(USER_COUNTRY_COOKIE)?.value; if (existing) { setLocationCookie(response, existing); return response; }`. Combine this with reordering `detectCountry` to check `detectCountryFromHeaders` first — with headers first, the cold path also stops depending on a network round-trip, which is the larger of the two wins. Skip the redirect-status special case from the original proposal; it is unnecessary since cookies on redirects are honoured.

### currentSelection/alternatives are persisted but currentSelectionIndex is not, so the applied Alternative is mislabelled and then silently discarded

`src/application/stores/holidays.ts:521` · 

**Fails when:** User applies Alternative 3 and reloads. Between hydration and the worker's first result, ManagementBar renders Alternative 3's days and metrics inside the card labelled "Option 1" and PlannerPanel disables Option 1's button as `alreadyApplied` while the real Option 3 offers `applyAlternative`. When the worker result arrives, `setCalculationResult` reads `currentSelectionIndex === 0`, sets `currentSelection` back to the base Suggestion, and the applied Alternative is dropped with no notice — while the Manual Days the user picked on top of it are preserved and re-layered onto a different plan. Pressing "reset manual changes" before that point reverts to the base Suggestion for the same reason.

**Why it is real:** All cited lines say what the finding claims, and the asymmetry is a real defect rather than a style call — the store already contains explicit code whose whole purpose is to preserve the applied Alternative, and not persisting the index defeats it across a reload.

Verified: partialize (holidays.ts:493-535) writes `holidays`, `suggestion`, `maxAlternatives`, `alternatives`, `currentSelection`, `manuallySelectedDays`, `removedSuggestedDays` — and omits `currentSelectionIndex`, `previewAlternativeIndex`, `previewAlternativeSelection`. After rehydration those three fall back to the initial state (holidays.ts:85-86), i.e. 0.

Every consumer keys off the index, as claimed:
- ManagementBar.tsx:71-73 builds `allSuggestions` by substituting `currentSelection` into slot `currentSelectionIndex` — with the index at 0 the applied Alternative's days/metrics get rendered inside the "Option 1" card, and line 116 literally prints `currentSelectionIndex + 1`.
- PlannerPanel.tsx:243-249 uses `disabled={currentSelectionIndex === currentIndex}` and the `alreadyApplied` label, so Option 1 is marked applied while the genuinely applied option shows as un-applied.
- `resetManualSelection` (holidays.ts:454) resolves `currentSelectionIndex === 0 ? suggestion : alternatives[index - 1]`, so the reset button reverts to the base Suggestion.
- `setCalculationResult` (holidays.ts:290-293) reads `currentSelectionIndex` (0) and overwrites `currentSelection` with the base suggestion when the mount recalculation returns. That code was clearly written to survive recalculation; the missing persist key is what breaks it.

I could not find a guard: `useStoresReady` only gates on `persist.hasHydrated()`, and ManagementBar's `isReady` (line 78) is satisfied by the persisted suggestion, so the panel does render with the wrong index during the window before the worker responds. CalendarList.tsx:80-91 always fires a recalculation on mount, so the discard is guaranteed, not merely possible.

Medium (not high) because the recalculation regenerates deterministically-equivalent alternatives, so the user can re-apply their option — nothing is unrecoverable; and the mislabelling window is short.

**Fix:** Add `currentSelectionIndex: state.currentSelectionIndex` to the partialize block (holidays.ts:493-535), and in `onRehydrateStorage` (holidays.ts:546+) clamp and mirror it: `const idx = state.currentSelectionIndex ?? 0; state.currentSelectionIndex = idx <= state.alternatives.length ? idx : 0; state.previewAlternativeIndex = state.currentSelectionIndex; state.previewAlternativeSelection = state.currentSelection;` — the clamp matters because `maxAlternatives` may have shrunk between sessions. The equally valid alternative is to stop persisting `suggestion`/`alternatives`/`currentSelection` and let the mount recalculation rebuild them; what must not stay is persisting a selection object without the index that names it.

### Homepage "smart bridges" demo hardcodes Spanish weekday initials for every locale

`src/ui/modules/pages/homepage/sections/Features.tsx:42` · 

**Fails when:** Load /de (or /en, /fr, /it) and scroll to #features. ### A new Worker is spawned and the in-flight one terminated on every recalculation, including every manual day click

`src/ui/hooks/useCalculationsWorker.ts:31`

Refuted on three counts. (1) The central premise - 'recreation buys nothing that the existing request-id guard does not' - is false. The worker's handler (worker.ts:10-122) is entirely synchronous, so a reused worker cannot preempt an in-flight run: queued messages sit behind it and execute serially to completion. terminate() is the only mechanism that actually cancels a long-running computation, which is precisely the standard idiom for a compute-heavy worker. Under the proposed fix, dragging the slider 15 steps would run 15 full computations back to back and the user would wait for all of them before seeing the latest result - strictly worse latency than what is there today. The requestId guard (line 42) discards stale *results*; it does nothing about stale *work*, which is the expensive part. ### Country detection self-fetches /cdn-cgi/trace with force-cache, so one visitor's country is cached and served to everyone

`src/infrastructure/services/location/utils/strategies.ts:20`

The literal code reading is correct (strategies.ts:20 fetches `${env.NEXT_PUBLIC_SITE_URL}/cdn-cgi/trace` with `cache: 'force-cache'`, and detectCountry.ts:5-6 tries it first), but every step of the harm chain fails to hold. (1) `force-cache` is not a directive that writes into a shared cache — it is a browser HTTP-cache read mode. In workerd only `no-store`/`no-cache` have implemented semantics; other modes are rejected or ignored, and there is no shared store into which a per-visitor trace response would be written. (2) Even assuming the subrequest passes through Cloudflare's CDN cache, `/cdn-cgi/trace` is an extensionless `text/plain` response, which the default Cache Level (Standard, the config here — wrangler.toml declares no cache rules) does not store, so there is no cached entry to replay one visitor's `loc=` to another. (3) Next's Data Cache is not involved either: `detectCountry` is reached only from `src/middleware.ts:47` (grep confirms the single call site), and fetch cache options are inert in middleware — nothing lands in the R2 incremental cache. (4) The 'loc reflects the datacenter, not the visitor' claim is asserted with no evidence; Worker subrequests carry the original eyeball's connecting IP, and `/cdn-cgi/*` is reserved by Cloudflare so the subrequest is answered by the edge rather than re-entering the worker. (5) `detectCountryFromHeaders` is not dead code: `detectCountryFromCDN` swallows every failure (strategies.ts:36-39, returns '') so the header strategy runs whenever the trace call fails or returns no `loc=`. What survives is much smaller and non-security: the chain order contradicts docs/adr/0004 line 10 ('the edge exposes the visitor's country on the request, so no geolocation service is needed on the common path'), the fetch is pure waste in front of a header that is already on the request, and the README is stale (line 19 names `https://www.cloudflare.com/cdn-cgi/trace`, line 26 says the strategy is a client-side browser fetch that fails on SSR — neither matches the code).
